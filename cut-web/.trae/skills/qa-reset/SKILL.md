# QA Reset — 开发需求润色与结构化

> **v1.1 更新 (2026-09-03)**：新增 Quick Reference 快速查找表。

## Quick Reference（快速查找）

| 用户意图 | 交互模式 | 内容维度 | 直接执行？ | 输出形式 |
|---------|---------|---------|-----------|---------|
| "这是什么/怎么实现的" | **澄清咨询** | - | ✅ **直接回答** | 解释说明 |
| "帮我改这个/加个功能" | **单一执行** | 编码开发/测试验证 | ✅ **简洁确认后执行** | 代码变更 |
| "一堆问题/改这改那..." | **批量编排** | (多选) | ❌ **先整理再执行** | 编号清单+优先级 |
| "不是这个意思/理解偏了" | **纠偏反馈** | - | ❌ **重置重来** | 重新整理 |
| "值不值得做/A还是B" | **探索评估** | 需求设计 | ❌ **先评估** | 利弊分析+建议 |
| "卡住了/报错/跑不起来" | **阻断紧急** | - | ✅ **插队优先** | 立即修复 |
| "不要了/撤销/回滚" | **回退撤销** | - | ⚠️ **评估影响** | 回滚方案 |

### 模式组合速查

| 组合场景 | 处理方式 |
|---------|---------|
| 批量 + 阻断（一堆问题中有个卡住的） | 阻断项**插队最前**，其他暂停 |
| 澄清 + 执行（问清楚后直接改） | 先澄清，确认后转单一执行 |
| 纠偏 + 重新执行 | **先重置**旧理解，再重新整理 |
| 评估 + 执行（评估后决定做） | 先输出利弊分析，用户确认后转执行 |

### 五大内容维度速查

| 维度 | 典型输出 |
|------|---------|
| **需求设计** | 用户故事、验收标准、优先级排序 |
| **编码开发** | 任务清单、技术方案、代码骨架 |
| **测试验证** | 测试用例、验收 Checklist、覆盖范围 |
| **文档交付** | 文档结构、内容大纲、交付清单 |
| **运维部署** | 部署步骤、回滚方案、监控检查点 |

---

用户口述需求时往往表达不够精确，本 skill 充当「需求润色器」。采用**双层识别机制**：

- **第一层：交互模式识别** — 判断用户这次想怎么交互（澄清？执行？编排？纠偏？）
- **第二层：内容维度识别** — 判断具体属于哪个开发环节（需求设计？编码开发？测试？）

交互模式决定**怎么响应**，内容维度决定**用什么模板**。

## 触发时机

- 用户显式输入 `/qa-reset`
- 用户描述了开发相关需求，但表述零散、含糊、缺少关键约束
- 用户一次性抛出多个问题（批量列表）
- 在动手执行前，需求意图需要先对齐

---

## 第一层：七大交互模式

收到用户输入后，**第一步先判断属于哪种交互模式**，这决定了后续的响应方式。

| 模式 | 识别信号词 | 核心意图 | 响应策略 |
|------|-----------|---------|---------|
| 澄清咨询 | "怎么实现的/为什么/是什么/什么意思" | 搞清现状，不改代码 | 直接解释，不出修改清单 |
| 单一执行 | "帮我改/加/去掉这个" | 一个明确任务，直接做 | 简洁确认后执行，不过度展开 |
| 批量编排 | 多个问题/改动点混在一起 | 精准描述+排序+编排 | 编号归集→逐条展开→汇总确认 |
| 纠偏反馈 | "不是这个意思/理解偏了/重新整理" | 纠正之前的理解 | 重置上下文，重新整理，不接旧清单 |
| 探索评估 | "值不值得/好不好/A还是B/要不要" | 不确定做不做，先评估 | 输出利弊分析+建议，不出任务清单 |
| 阻断紧急 | "卡住了/装不上/报错了/跑不起来" | 阻断项需插队优先 | 优先处理阻断项，其他任务暂停 |
| 回退撤销 | "不要了/退回去/撤销/回滚" | 撤销已有改动 | 评估回退影响，确认后执行 |

### 模式组合规则

- 一个输入可以同时命中多个模式（如"批量编排 + 阻断紧急"：一堆问题中有个阻断项要插队）
- 命中「澄清咨询」时，**不要**输出修改清单模板，直接解释
- 命中「单一执行」时，**可以**跳过完整模板，简洁确认后直接做
- 命中「纠偏反馈」时，**先重置**之前的理解，再重新整理
- 命中「阻断紧急」时，阻断项**插队到最前**，其他任务暂停等待

## 第二层：五大内容维度

确认交互模式后，**第二步判断属于哪个内容维度**（可多选），决定用哪个模板展开。

| 维度 | 识别信号词 | 典型场景 |
|------|-----------|---------|
| 需求设计 | "想做/需要/应该有/能不能加/是否合理" | 新功能构思、产品方案讨论、架构评估 |
| 编码开发 | "改/修/调/加个/去掉/对齐" | 具体代码变更、Bug 修复、UI 调整 |
| 任务分拆 | "分几步/怎么排/先做啥/先分析再设计" | 大需求拆解为可执行子任务 |
| 阶段推进 | "下一步/继续/该干嘛了/卡住了" | 项目进度流转、阶段衔接 |
| 场景测试 | "测一下/验证/对不对/跑一遍/playwright" | 功能验证、边界测试、回归测试 |

---

## 模式一：澄清咨询

> 用户想搞懂现状，不是要改东西。

### 响应模板

```
## 澄清咨询 · 现状说明

### 1. 问题
用户想了解的问题。

### 2. 现状说明
- 实现方式：xxx（引用具体文件/函数）
- 工作流程：xxx
- 关键设计原因：xxx

### 3. 补充说明
- 如果用户后续可能想改这块，附一句"如果需要调整，可以说具体方向"

### 4. 待确认项
- ？xxx（如果用户的澄清问题本身有歧义）
```

---

## 模式二：单一执行

> 一个明确任务，直接做，不过度展开。

### 响应模板

```
## 单一执行 · 快速确认

### 1. 任务
一句话：帮用户做什么。

### 2. 理解确认（仅在有可能误解时）
- ？如果有理解不确定的地方，标注
- 如果完全明确，直接写"理解无误，开始执行"

### 3. 开始执行
```

> 原则：如果用户描述足够清晰，可以跳过模板直接执行，不要为了"走流程"而拖慢节奏。

## 模式三：批量编排

> 用户一次抛出多个问题，需要精准描述+排序+编排。

### 批量输入处理规则

#### 1. 编号归集
将每个独立问题提取出来，按出现顺序编号为 Q1、Q2、Q3...，标注所属交互模式+内容维度。

#### 2. 嵌套提问处理
如果某个问题内部还带着选择/反问（如"我给出两个方案"、"是否合理"），在该问题下方用缩进子项列出，并标注「待用户决策」。

#### 3. 流程提示处理
如果用户在末尾或中间给出了执行流程指示（如"先设计再开发再测试"），提取为「执行策略」，放在输出最前面，指导后续所有任务的处理顺序。

#### 4. 跨项目参考处理
如果用户引用了其他项目的文件/页面作为参考，标注「跨项目引用」，提取参考要点，不混淆当前项目上下文。

#### 5. 阻断项插队
如果批量问题中存在阻断项（如"端口被占了""依赖装不上"），插队到最前面优先处理，标注「阻断」。

### 输出编排顺序

```
1. 执行策略（提取用户的流程提示）
2. 问题总览表（编号 + 交互模式 + 内容维度 + 摘要 + 是否有待决策 + 是否阻断）
3. 逐条展开（按编号顺序，套用对应内容维度模板；阻断项排最前）
4. 汇总待确认项（把所有「？」集中列出）
5. 末尾确认语
```

### 问题总览表格式

| 编号 | 交互模式 | 内容维度 | 问题摘要 | 有待决策 | 是否阻断 |
|------|---------|---------|---------|---------|---------|
| Q1 | 单一执行 | 编码开发 | 页面标题优化 | 是 | 否 |
| Q2 | 单一执行 | 编码开发 | doc-manager 交互优化 | 否 | 否 |
| Q3 | 澄清咨询+单一执行 | 需求设计 | 主页视觉优化 | 否 | 否 |
| Q4 | 探索评估 | 需求设计 | 文件架构评估 | 是 | 否 |
| Q5 | 单一执行 | 场景测试 | Playwright 脚本 | 否 | 否 |

### 汇总待确认项格式

```
## 汇总待确认项
- Q1-？：xxx
- Q2-？：xxx
  …
以上理解对吗？有没有要补充或修正的？
```

## 模式四：纠偏反馈

> 用户纠正之前的理解偏差。

### 响应模板

```
## 纠偏反馈 · 重新整理

### 1. 之前的理解（标记为已废弃）
~~之前的理解：xxx~~

### 2. 用户纠正点
- 纠正1：xxx
- 纠正2：xxx

### 3. 重新整理后的理解
按用户纠正后的意图，重新套用对应内容维度模板输出。

### 4. 确认
「这次理解对吗？」
```

> 原则：不要在旧理解上修补，直接重置重来。标注清楚"之前理解已废弃"。

---

## 模式五：探索评估

> 用户不确定要不要做，先评估。

### 响应模板

```
## 探索评估 · 利弊分析

### 1. 评估问题
用户在犹豫什么。

### 2. 利弊分析
| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| 方案A | xxx | xxx | xxx |
| 方案B | xxx | xxx | xxx |

### 3. 建议
推荐方案X，因为 xxx。
（但最终决策权在用户）

### 4. 待确认项
- ？用户决定后是否继续推进
```

> 原则：不替用户做决定，但给出有依据的建议。不出任务清单，除非用户确认要做。

---

## 模式六：阻断紧急

> 阻断项需插队优先处理。

### 响应模板

```
## 阻断紧急 · 优先处理

### 1. 阻断问题
xxx（当前阻断项）

### 2. 影响范围
- 被阻塞的任务：xxx
- 不受影响的任务：xxx（可以并行做的）

### 3. 解决方案
- 方案：xxx
- 预计耗时：xxx

### 4. 解决后
阻塞解除后，继续之前的任务编排。
```

> 原则：阻断项插队到最前，其他任务暂停。如果批量输入中混有阻断项，阻断项优先输出。

---

## 模式七：回退撤销

> 用户要撤销已有改动。

### 响应模板

```
## 回退撤销 · 影响评估

### 1. 要撤销的改动
xxx（具体改了什么）

### 2. 回退影响
- 受影响文件：xxx
- 受影响功能：xxx
- 是否有依赖该改动的后续改动：xxx

### 3. 回退方式
- 方式：xxx（git revert / 手动恢复 / 删除新增文件）

### 4. 确认
「确认要回退以上内容吗？回退后这些功能将恢复原状。」
```

> 原则：先评估影响再执行回退，特别是连锁影响（A改了→B基于A又改了→回退A会影响B）。

## 交互流程

1. 收到用户输入 → **第一层：识别交互模式**（可多选）
2. **第二层：识别内容维度**（可多选）
3. 根据交互模式决定响应方式：
   - 澄清咨询 → 直接解释，不出修改清单
   - 单一执行 → 简洁确认后执行
   - 批量编排 → 输出执行策略 + 总览表 + 逐条展开 + 汇总确认
   - 纠偏反馈 → 重置旧理解，重新整理
   - 探索评估 → 输出利弊分析 + 建议
   - 阻断紧急 → 插队优先处理
   - 回退撤销 → 评估影响后确认执行
4. 根据内容维度选择模板展开
5. 末尾确认语（除非是澄清咨询类，直接回答即可）
6. 用户确认后 → 进入实际执行
7. 如果用户确认时有补充/修正 → 更新后重新确认

## 注意事项

- **先润色再执行**：核心原则，不要跳过整理直接干活（澄清咨询和单一执行除外）
- **双层识别**：先判断"怎么响应"（交互模式），再判断"用什么模板"（内容维度）
- **不过度展开**：澄清咨询直接回答，单一执行简洁确认，不要为了走流程而拖慢节奏
- **模糊就标「？」**：用户表述不清的地方，标注理解假设
- **批量问题不遗漏**：逐条编号、逐条展开、最后汇总待确认项
- **嵌套提问单独标出**：问题内部的选择/反问标「待用户决策」
- **阻断项插队**：批量中混有阻断项，阻断项优先输出
- **纠偏要重置**：不要在旧理解上修补，直接重来
- **跨项目引用不混淆**：标注「跨项目引用」，提取参考要点但不混入变更范围
- **语言跟随用户**：用中文输出，和用户语言保持一致
- **项目上下文**：结合项目实际情况（如漫剧剪辑师的 Step1~7 工作流、FastAPI 后端结构），让影响范围判断更准确
