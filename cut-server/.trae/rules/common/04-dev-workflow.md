# 开发工作流（通用）

> 本规范适用于所有软件开发项目，可直接复制使用。

## 1. 零干预开发流程

> 目标：用户仅在项目启动时填写一次初始化问卷，后续由 AI 自主驱动开发、自追踪、自验证，实现零人员干预。

### 1.1 项目启动流程

```
用户填写问卷 → AI 读取问卷+参考资料 → AI 生成项目上下文 → AI 生成 plan 骨架 → AI 自主开发
```

1. **用户填写 `plan/00-项目初始化问卷.md`**（唯一需要人工的步骤）
   - 模板见 `.trae/rules/common/templates/00-项目初始化问卷.md`
   - 填写技术选型、业务功能、参考资料路径、自主决策授权等
   - 不确定的项可填"由 AI 决策"

2. **AI 读取问卷并生成项目上下文**
   - 读取问卷全部内容
   - 如有参考项目目录，读取学习其架构和风格
   - 如有设计文档目录，提取功能点
   - 生成 `plan/00-项目上下文.md`（规范见本文 §8）

3. **AI 生成 plan 目录骨架**
   - 根据 `00-项目上下文.md` 的功能点清单，初始化各方向文件
   - `02-任务列表.md` 生成任务拆分
   - `01-开发进度.md` 生成里程碑
   - `07-需求对应.md` 生成需求映射表

4. **AI 自主驱动开发**
   - 每次工作前读取 `00-项目上下文.md` 功能点清单
   - 找到第一个非 `done` 的功能点，按状态执行对应动作
   - 完成后更新状态，同步更新相关 plan 文件
   - 遇到不确定时按自主决策规则处理，不暂停等待人工

### 1.2 功能点状态驱动

AI 通过功能点状态自主决定下一步动作，无需人工调度：

| 当前状态 | AI 执行动作 | 完成后切换 | 同步更新 |
|---------|-----------|-----------|---------|
| pending | 设计方案，拆解任务 | → designing | 02-任务列表, 01-开发进度 |
| designing | 编写代码实现 | → developing | 08-代码日志, 04-接口文档 |
| developing | 编写并执行单元测试 | → testing | 05-单元测试 |
| testing | 功能验证，更新映射 | → done | 06-功能测试, 07-需求对应 |

详细规则见本文 §8。

### 1.3 自主决策规则

AI 遇到不确定情况时，按以下优先级处理，**不暂停等待人工**：

1. 查阅 `00-项目上下文.md` 已有决策记录
2. 查阅 `.trae/rules/` 规则约束
3. 查阅问卷提供的参考资料
4. 按最佳实践自主决策，记录到 `03-问题记录.md`（含背景、决策、依据、影响）
5. 继续执行

> 人工可在事后审阅 `03-问题记录.md` 中的决策记录，如有异议可修改 `00-项目上下文.md` 调整后续行为。

### 1.4 检查点自验证

AI 在以下节点自动执行自验证，确保功能点对齐：

| 检查点 | 验证内容 | 不通过时 |
|--------|---------|---------|
| 设计完成 | 任务拆解完整、无遗漏功能点 | 补充任务后继续 |
| 编码完成 | 代码符合规范、接口已定义 | 修复后继续 |
| 单测完成 | 覆盖率达标、所有用例通过 | 补充用例后继续 |
| 功能完成 | 需求对应表全部标记完成 | 回到未完成项继续 |

> 修复过程中如反复失败，自动触发卡点恢复机制，详见本文 §9。

### 1.5 轻量模式 vs 完整模式

并非所有任务都需要走完整零干预流程。模式的判定依据是**变更性质**，而非文件数量。

#### 1.5.1 判定标准

按变更性质分类，而非文件数量：

| 变更类型 | 模式 | 典型场景 | 说明 |
|---------|------|---------|------|
| Bug 修复 | 轻量 | 居中未对齐、点击无响应、报错修复 | 修复已有功能缺陷，不新增功能 |
| 代码质量 | 轻量 | 格式化、补充注释、提取全局变量 | 机械性改动，无逻辑变化 |
| 重构 | 轻量 | 重命名、提取方法、移动代码位置 | 不改变外部行为，仅优化内部结构 |
| 配置调整 | 轻量 | 修改超时时间、调整日志级别 | 仅改配置项，无代码逻辑变化 |
| 新功能 | **完整** | 新增评测方向、新增接口、新增页面 | 引入新的业务能力 |
| 数据库变更 | **完整** | 新增表、新增字段、数据迁移 | 影响数据结构，需设计评审 |
| 架构调整 | **完整** | 新增模块/层级、改变数据流向 | 影响整体架构，需设计评审 |
| 依赖变更 | **完整** | 新增/升级/替换 pip 包 | 可能影响兼容性，需评估 |
| 跨模块逻辑 | **完整** | 修改涉及 3 个以上模块的业务逻辑 | 影响范围大，需拆解任务 |

#### 1.5.2 模式流程

| 模式 | 执行步骤 | plan 文件更新 |
|------|---------|-------------|
| **轻量模式** | 跳过 §1.1（启动流程）、§1.2（状态驱动）、§1.3（自主决策），直接编码 + §1.4（自验证）+ §9（卡点检测） | 仅更新 `08-代码日志.md` |
| **完整模式** | 完整零干预流程 §1.1-§1.4 | 全部相关 plan 文件 |

> 轻量模式跳过"读取上下文→状态驱动→自主决策"三步，直接编码+验证。但仍受卡点检测（本文 §9）约束。

#### 1.5.3 模式切换规则

- 轻量模式中发现需要新增接口/数据库变更/架构调整 → **自动切换为完整模式**
- 用户提出的模糊问题（如"居中未对齐"），AI 先排查定位，**根据根因判定模式**：
  - 根因是 CSS 样式问题 → 轻量模式
  - 根因是组件逻辑需重构 → 完整模式
- 无法确定模式时，默认按完整模式处理

> 核心原则：**变更性质决定模式，而非文件数量。** 全项目格式化虽然涉及多文件，但属于轻量模式；单个文件新增 API 接口，属于完整模式。

### 1.6 依赖管理规则

- 新增依赖必须在 `08-代码日志.md` 中记录：包名、版本、用途
- 依赖版本必须锁定（`requirements.txt` 使用 `==` 精确版本）
- 新增依赖前检查是否与现有依赖冲突（运行 `pip check`）
- 禁止引入与现有依赖功能重复的包
- 开发依赖（pytest、mypy 等）与生产依赖分开管理

## 2. 项目目录规范

### 2.1 /docs 目录（需求设计文档）

- `/docs` 目录用于存放**需求设计文档**
- **合理规划，不盲目增加文件**：
  - 每个独立功能模块或需求批次对应一个文档
  - 文档命名清晰：`docs/<模块名>_<需求简称>.md`（如 `docs/eval_task_batch_run.md`）
  - 文档内容应包含：需求背景、方案设计、接口定义、数据模型、验收标准
- **禁止**将临时笔记、会议纪要等非正式文档放入 `/docs`
- **禁止**为同一个模块创建多个零散文档，应在同一文档内迭代

### 2.2 /plan 目录（项目计划与过程文档）

- `/plan` 目录用于存放**项目计划与过程跟踪文档**，通过一组固定方向的文件完整控制项目进度与功能点对齐
- **文件按方向编号命名，不按模块拆分**：每个方向一个文件，覆盖全局
- **不重复增加文件**：方向的划分是固定的，新需求不需要新建文件，而是在对应方向文件内追加更新
- **每次新增功能需求时，必须逐一审视 `/plan` 目录下所有文件**，判断哪些文件需要同步更新：

#### 2.2.1 推荐方向划分

| 编号 | 文件名 | 方向 | 职责 |
|------|--------|------|------|
| 00 | `00-项目初始化问卷.md` | 初始化问卷 | 用户唯一需填写的文件，AI 据此生成项目上下文（**模板在 `common/templates/` 下**，复制到 plan/ 后填写） |
| 00 | `00-项目上下文.md` | 项目上下文 | AI 自动生成的第一读取文件，含功能点清单和决策记录（规范见本文 §8） |
| 01 | `01-开发进度.md` | 开发进度 | 整体开发阶段、里程碑、当前进展、阻塞项 |
| 02 | `02-任务列表.md` | 任务拆解 | 需求拆分的开发任务清单、状态、负责人、优先级 |
| 03 | `03-问题记录.md` | 问题记录 | 开发过程中遇到的问题、自主决策记录、待解决事项 |
| 04 | `04-接口文档.md` | 接口文档 | 对外/对内 API 定义、变更记录 |
| 05 | `05-单元测试.md` | 单元测试 | 单测覆盖计划、用例清单、执行结果 |
| 06 | `06-功能测试.md` | 功能测试 | 功能测试场景、验收用例、测试结果 |
| 07 | `07-需求对应.md` | 需求对应 | 需求条目与代码实现、任务的映射关系，确保功能点不遗漏 |
| 08 | `08-代码日志.md` | 代码日志 | 代码变更摘要、重要提交记录、版本变更说明 |

> 以上方向为推荐划分，具体项目可根据实际情况调整编号和文件名，但**方向覆盖应完整**，确保进度可控、功能可追溯。

#### 2.2.2 更新规则

- **新需求开发前**：先查看 `02-任务列表.md` 拆解任务，同步更新 `01-开发进度.md`
- **开发过程中**：遇到问题记录到 `03-问题记录.md`，接口变更更新 `04-接口文档.md`
- **开发完成后**：更新 `05-单元测试.md` 和 `06-功能测试.md` 的执行结果，在 `07-需求对应.md` 中标记完成
- **内容发生较大变化时**：`03-问题记录.md`（问题记录）、`01-开发进度.md`（进度变化）、`05-单元测试.md`（单测完善）、`06-功能测试.md`（功能测试调整）可能都需要同步更新
- **每次提交后**：在 `08-代码日志.md` 追加变更摘要

#### 2.2.3 变更追加格式

在文件内按日期追加变更，标注变更摘要：

```markdown
---

## 2026-08-12: 新增 RAG 评测方向支持

**变更摘要：**
- 新增 RAG 评测管理器，扩展评测方向配置
- 影响文件：managers/rag_eval_manager.py（新增）、services/eval_service.py（修改）
- 同步更新：开发进度、任务列表、接口文档、单元测试
```

#### 2.2.4 plan 文件内容规范

每个 plan 文件应包含以下结构要素，确保 AI 生成的 plan 文件规范、可执行、可追溯：

**通用要求（所有 plan 文件）：**
- 文件开头有**统计概览表**（总数、按状态/优先级分布），一眼看清整体情况
- 文件末尾有**变更记录区**，按日期追加，保留历史
- 使用**编号体系**实现交叉引用：需求 `REQ-001`、任务 `T-001`、问题 `P-001`、单测 `UT-001`、功能测试 `FT-001`，编号可互相查找

**各文件特定结构：**

**01-开发进度.md：**
```markdown
## 总览（阶段状态表 + 完成度百分比）
## 各阶段详情（每阶段含：任务表 + 完成标准 checkbox）
## 里程碑追踪（M1/M2/... 状态）
## 进度更新日志（按日期追加）
## 风险与应对（概率 + 影响 + 应对方案）
```

**02-任务列表.md：**
```markdown
## 状态说明（⏳待开始 🔄进行中 ✅已完成 ❌阻塞 📝待确认）
## 任务统计（按阶段 + 优先级）
## 任务详情（每个任务含：状态、优先级、预估工时、依赖任务、验收标准 checkbox）
```

**03-问题记录.md：**
```markdown
## 状态说明（待确认/待解决/已解决/已关闭）
## 问题统计（按状态 + 风险等级）
## 风险预研（主动预判潜在问题 + 应对方案）
## 问题详情（每个问题含：描述、根因分析、解决方案、解决时间）
## 卡点记录（卡点恢复机制写入，见本文 §9.2.1）
## 回滚记录（严重卡点跳过时写入，见本文 §9.4.1）
## 问题模板（供复制粘贴的新增模板）
```

**04-接口文档.md：**
```markdown
## 通用约定（Base URL、CORS、状态码、错误格式）
## 接口列表（每个接口含：Method、Path、参数、请求示例、响应示例、错误码）
## 数据模型（Schema 定义）
## 变更记录（按日期追加，标注影响范围）
```

**05-单元测试.md：**
```markdown
## 测试策略（核心覆盖、边界优先、Mock 外部、异步测试）
## 分模块覆盖率目标（每个模块独立目标）
## 测试用例清单（编号 + 模块 + 用例名 + 优先级）
## 测试数据准备（所需文件 + Mock 场景）
## 执行命令（实际 pytest 命令）
## 测试输出目录规范（日期+时间戳）
```

**06-功能测试.md：**
```markdown
## 测试环境（服务版本、依赖配置）
## 测试用例（按功能分类，端到端视角，非按模块拆分）
## 验证方案（卡点恢复机制写入，见本文 §9.2.2）
## 性能测试（具体量化指标 + 验收标准）
## 兼容性测试（不同输入来源/环境）
## 安全测试（注入、越权、异常输入）
## 分级执行计划（冒烟 P0 → 全面 P0+P1 → 完整全部）
```

**07-需求对应.md：**
```markdown
## 追溯矩阵（需求ID → 描述 → 来源 → 开发任务 → 测试用例 → 状态）
## 按模块覆盖率统计（每模块需求数 + 覆盖率）
## 优先级分布（P0/P1/P2 占比）
## 阶段对应（每开发阶段涵盖哪些需求）
## 需求变更记录（变更原因 + 影响范围）
```

**08-代码日志.md：**
```markdown
## 变更记录（按日期追加，每条含：变更摘要、影响文件、关联任务/需求ID）
## 依赖变更记录（包名、版本、用途、变更类型）
```

## 3. Git 提交规范

### 3.1 提交信息格式

```
<type>(<scope>): <subject>

<body>

<footer>
```

### 3.2 Type 类型

| Type | 说明 |
|------|------|
| feat | 新功能 |
| fix | Bug 修复 |
| docs | 文档变更 |
| style | 代码格式调整（不影响功能） |
| refactor | 重构（不新增功能，不修 Bug） |
| perf | 性能优化 |
| test | 测试相关 |
| chore | 构建/工具/依赖等辅助变更 |

### 3.3 示例

```
feat(eval): 支持RAG评分评测方向

- 新增 RAG 评测管理器
- 扩展评测方向配置
- 支持文件导入测试集

Closes #123
```

### 3.4 提交原则

- 每次提交只做一件事
- 提交信息用中文或英文均可，但项目内保持一致
- 不提交无法运行的代码
- 不提交大文件和临时文件

## 4. 分支策略

### 4.1 分支类型

| 分支 | 命名 | 用途 |
|------|------|------|
| 主分支 | `main` / `master` | 稳定可用的代码 |
| 开发分支 | `develop` | 集成分支（可选） |
| 功能分支 | `feature/<功能描述>` | 新功能开发 |
| 修复分支 | `fix/<问题描述>` | Bug 修复 |
| 发布分支 | `release/<版本号>` | 发布准备 |
| 热修复分支 | `hotfix/<问题描述>` | 线上紧急修复 |

### 4.2 功能开发流程

```
main → feature/xxx → 开发 → PR → 审查 → 合并到 main
```

### 4.3 分支命名示例

```
release/v1.0.0
```

## 5. 版本管理

### 5.1 版本号格式

遵循语义化版本（Semantic Versioning）：

```
MAJOR.MINOR.PATCH
```

- **MAJOR**：不兼容的 API 变更
- **MINOR**：向下兼容的功能性新增
- **PATCH**：向下兼容的问题修正

### 5.2 示例

- `1.0.0` - 首个正式版本
- `1.0.1` - 修复 Bug
- `1.1.0` - 新增功能
- `2.0.0` - 重大变更，不兼容旧版

## 7. 问题排查

### 7.1 遇到问题时

1. 先查看日志，通过事务 ID 定位完整调用链路
2. 检查配置是否正确
3. 复现问题，确认触发条件
4. 搜索 Issue / FAQ 是否有同类问题
5. 最小化复现场景
6. 无法解决时及时求助，附上：
   - 错误堆栈

   - 环境信息

### 7.2 Bug 报告规范

- **复现步骤**：清晰的步骤

- **实际结果**：实际是什么样
- **错误日志**：完整的错误堆栈
- **附件**：相关文件、截图等

## 9. 卡点检测与恢复机制

> 本节强制生效。AI 在开发过程中必须持续自检是否陷入卡点，一旦检测到则触发恢复流程。

### 9.1 卡点检测

**检测时机**：每次执行修复操作前，必须进行卡点自检。

**判定标准**（满足任意一条即触发）：

| 条件 | 阈值 | 说明 |
|------|------|------|
| 同一文件修改次数 | ≥ 3 次 | 针对同一文件反复修改仍未通过 |
| 同一错误类型出现 | ≥ 2 次 | 相同或相似的错误信息重复出现 |
| 同一问题对话轮次 | ≥ 5 轮 | 围绕同一问题的对话超过 5 轮仍未解决 |
| 修复后测试仍失败 | ≥ 2 次 | 修复后运行测试，同一测试连续 2 次以上未通过 |
| 回滚或重做同一改动 | ≥ 2 次 | 对同一段代码反复应用/回滚 |

**检测动作**：立即停止修复 → 告知用户触发卡点恢复 → 进入恢复流程。

### 9.2 恢复流程

```
检测到卡点 → 停止修复 → 汇总失败记录 → 生成验证方案 → 方案评审 → 执行修复 → 多维度验证 → 通过则继续
```

#### 9.2.1 第一步：汇总失败记录

写入 `03-问题记录.md`：

```markdown
### 卡点记录 - [日期时间]

**问题描述**：一句话描述卡住的问题
**卡点触发原因**：命中哪条判定标准

**失败尝试汇总**：
| 序号 | 尝试方案 | 失败原因 | 错误信息 |
|------|---------|---------|---------|
| 1 | 方案A | 原因 | 错误日志摘要 |
| 2 | 方案B | 原因 | 错误日志摘要 |

**共性分析**：
- 所有失败尝试的共同点
- 可能的根本原因假设
```

#### 9.2.2 第二步：生成验证方案

写入 `06-功能测试.md`：

```markdown
### 验证方案 - [问题简称] - [日期时间]

#### 1. 任务定义
- **修复目标**：明确要解决的具体问题
- **修复范围**：涉及的文件和模块

#### 2. 合格标准（必须全部可验证）
| 编号 | 验证项 | 标准 | 验证方式 |
|------|--------|------|---------|
| V01 | 错误不再出现 | 运行后无目标错误 | 单元测试 |
| V02 | 功能正常 | 核心功能可正常使用 | 功能测试 |
| V03 | 无回归 | 原有功能不受影响 | 回归测试 |
| V04 | 输出正确 | 输出结果符合预期 | 输出物检测 |

#### 3. 输出物检测方式
- [ ] 文字输出：检查日志/返回值文本内容
- [ ] 程序运行：直接运行程序观察实际行为
- [ ] 截图对比：通过浏览器自动化截图，前后对比
- [ ] 交互效果：通过浏览器模拟操作，验证交互行为
- [ ] 数据状态：检查数据库/文件状态变化

#### 4. 通过条件
- 所有验证项全部通过，方可判定问题已解决
- 任何一项未通过，回到第一步重新分析
```

#### 9.2.3 第三步：方案自评审

- [ ] 合格标准是否**具体、可验证**（禁止"基本可用"等模糊标准）
- [ ] 验证方式是否**可执行**（有具体命令或操作步骤）
- [ ] **验证手段是否匹配问题类型**（UI 问题不能只靠单测，必须含截图/交互验证）
- [ ] 是否覆盖了之前所有失败的场景
- [ ] 是否考虑了边界情况和回归风险

#### 9.2.4 第四步：执行修复

1. 选择与之前失败方案**不同**的思路
2. 每步修改后立即运行对应的验证项
3. 任何一步验证失败，立即停止，回到第一步重新分析

#### 9.2.5 第五步：多维度验证

**AI 必须主动选择最有效的验证手段，而非只跑单元测试。**

**验证手段选择策略**：

| 问题类型 | 首选验证手段 | 说明 |
|---------|------------|------|
| 纯逻辑/算法错误 | 单元测试 | 逻辑可隔离验证，单测最快 |
| API 接口问题 | 程序运行 + 接口调用 | 启动服务，实际调用接口看返回 |
| 页面渲染/UI 问题 | **浏览器截图对比** | 单测无法看到渲染效果，必须截图 |
| 交互行为问题 | **浏览器模拟操作** | 点击、输入、跳转等交互必须实际操作验证 |
| 数据流/集成问题 | 程序运行 + 数据状态检查 | 端到端运行后检查数据库/文件状态 |
| 配置/环境问题 | 程序运行 + 日志检查 | 实际运行看日志输出 |

**验证手段升级规则**：

```
单元测试 → 不充分 → 程序运行验证 → 不充分 → 浏览器截图/交互验证
```

升级触发条件（满足任一即升级）：
- 单元测试通过但问题仍然存在 → 升级到程序运行
- 程序运行后无法确认效果 → 升级到浏览器截图验证
- 涉及 UI 渲染、页面跳转、交互效果 → 直接使用浏览器验证，不走单测
- 已修复 2 次以上单测通过但用户反馈仍有问题 → 必须用浏览器截图验证

**浏览器验证方法**：
1. **截图验证**：启动服务 → 浏览器打开页面 → 截图 → 对比预期效果
2. **交互验证**：模拟用户操作 → 截图每一步 → 确认行为正确
3. **网络验证**：查看网络请求 → 确认 API 调用和返回正确
4. **控制台验证**：查看控制台日志 → 确认无 JS 错误

> 工具选择：优先使用项目已有的浏览器自动化工具（如 Playwright MCP、browser_use agent 等）。

**验证维度矩阵**：

| 维度 | 验证方法 | 通过标准 | 适用场景 |
|------|---------|---------|---------|
| 单元测试 | 运行 pytest 相关测试 | 全部通过 | 纯逻辑、数据处理 |
| 程序运行 | 启动服务，实际执行 | 无报错，行为正常 | API、服务端逻辑 |
| 浏览器截图 | 打开页面截图对比 | 视觉效果符合预期 | UI 渲染、页面布局 |
| 浏览器交互 | 模拟操作并截图 | 交互行为正确 | 表单、按钮、跳转 |
| 数据状态 | 检查数据库/文件 | 数据正确变更 | 持久化、文件操作 |
| 回归测试 | 运行全量或相关测试 | 无新增失败 | 所有修复 |

**全部通过** → 问题解决，更新 `03-问题记录.md` 标记已解决
**任一未通过** → 回到 9.2.1 重新分析

### 9.3 对话历史分析

AI 应主动利用对话历史和 memory 系统：
1. **会话开始时**：检查 memory 中是否有当前项目的卡点记录
2. **修复前**：回顾最近 5-10 轮对话，判断是否在同一问题上打转
3. **第一次修复失败后**：提示"如果再次失败将触发卡点恢复机制"
4. **发现修复方案与之前失败方案相似时**：明确提示并建议换思路

### 9.4 卡点升级机制

恢复流程执行 1 轮后仍未解决（第二轮卡点）：

1. **执行回滚**（见 §9.4.1），将代码恢复到阻塞前状态
2. **升级为严重卡点**，记录到 `03-问题记录.md`
3. **跳过当前问题**，标记为 blocked，继续下一个功能点
4. **在 `01-开发进度.md` 中标注阻塞项**
5. **等待新对话时优先汇报阻塞项**

#### 9.4.1 回滚策略

1. **保存现场**：将当前所有修改的 diff 保存到 `03-问题记录.md`
2. **回滚代码**：
   - 如使用 Git：`git stash` 暂存当前修改，记录 stash ID
   - 如未使用 Git：逐文件恢复到修改前状态
3. **验证回滚**：回滚后运行基础测试，确认代码库恢复到可工作状态
4. **记录回滚信息**：

```markdown
### 回滚记录 - [日期时间]
- **关联卡点**：[卡点记录标题]
- **回滚方式**：git stash / 手动恢复
- **stash ID / diff 位置**：[标识信息]
- **回滚验证**：基础测试通过/失败
- **后续恢复方法**：git stash pop / 从记录中恢复 diff
```

5. **后续重新尝试时**：先读取回滚记录中的失败方案和 diff，避免重复同样错误

### 9.5 规则执行优先级

本节**优先级高于常规开发流程**：
- 检测到卡点 → 立即中断当前操作 → 执行恢复流程
- 恢复流程未完成 → 不允许开始新的功能点开发
- 验证方案未通过 → 不允许标记问题已解决

> 卡点恢复机制是问题修复的**紧急验证**，与 §1.4 检查点自验证（常规验证）配合使用。
