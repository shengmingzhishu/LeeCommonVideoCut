# Python 代码审查

## 技能目标

当 Python 代码已经基本完成，需要在提交、合并或交付前做一次高质量代码检查时，使用本技能。

本技能的目标不是泛泛而谈，也不是重写整个功能，而是通过 AI 自动化编程工具，对已完成代码进行面向风险的审查，优先识别真实缺陷、回归风险和测试缺口。

## 审查原则

- 优先审查本次改动涉及的文件，以及直接受影响的调用点。
- 优先报告会导致错误、漏洞、回归或线上风险的问题。
- 风格类建议只有在影响可维护性、可读性或容易引发缺陷时才提出。
- 所有结论都应基于实际代码路径，避免猜测式审查。
- 如果没有发现明确问题，需要明确说明“未发现具体缺陷”，同时指出剩余风险和测试空白。

## 审查顺序

按以下优先级进行检查：

1. 正确性
   - 业务逻辑是否正确
   - 条件分支是否完整
   - 边界值是否处理
   - 输入校验是否缺失
   - 异常路径是否正确

2. 稳定性
   - 资源是否正确释放
   - 重试、循环、递归是否存在失控风险
   - 超时、取消、回滚、清理逻辑是否完整
   - 并发或异步逻辑是否存在竞态问题

3. 安全性
   - 是否存在注入风险
   - 是否有不安全反序列化
   - 是否泄露敏感信息
   - 是否缺少权限校验
   - 文件、命令、路径处理是否安全

4. 可维护性
   - 函数是否过长或职责混乱
   - 是否有重复逻辑
   - 命名是否掩盖真实行为
   - 是否存在隐式耦合
   - 是否缺少关键类型约束或接口约束

5. 测试覆盖
   - 修改的逻辑是否有测试
   - 修复类改动是否有回归测试
   - 错误分支和边界分支是否未覆盖

6. 性能
   - 是否有重复查询、重复请求
   - 是否有明显的 N+1 问题
   - 是否存在可避免的大对象加载或全量遍历
   - 异步代码中是否混入阻塞操作

## Python 专项检查清单

审查 Python 代码时，必须重点检查以下内容：

- `None` 和可选值处理是否安全
- 是否使用了可变默认参数
- 是否存在过宽的 `except Exception` 或吞异常行为
- 上下文管理器是否使用正确
- 是否使用了不安全的 `eval`、`exec`、`pickle`、`yaml.load`
- 是否存在危险的 shell 调用或命令拼接
- `async` 函数里是否执行阻塞 I/O
- 时间、时区、时间戳处理是否一致
- ORM 查询是否低效，是否可能出现 N+1
- 输入边界、数据结构、字段格式是否有校验
- 日志、错误信息中是否输出令牌、密码、密钥、个人信息
- 动态类型是否掩盖了明显的类型错配问题

## 推荐工作流

1. 识别本次功能或修复涉及的改动文件。
2. 阅读核心实现，以及最接近的调用方或入口。
3. 检查是否存在对应测试，尤其是新增逻辑和异常路径。
4. 如果仓库提供可执行验证命令，优先运行最小范围验证。
5. 输出按严重程度排序的审查结论，并给出明确修复建议。

## 创建审查结果目录

在完成代码检查后，需将审查结果文档输出到当前项目根目录下的 `.changes/review` 目录中。

按以下规则组织产物：

1. 若不存在 `.changes` 目录，则创建 `.changes`。
2. 若 `.changes` 下不存在 `review` 目录，则创建 `.changes/review`。
3. 在 `.changes/review` 下创建本次审查结果文件，命名格式为 `代码检查-${需求名称或变更名称}-${当前日期}.md`。
4. 如果本次审查没有明确需求名称，可使用改动主题、分支主题或模块名称替代 `${需求名称或变更名称}`。
5. 示例：`代码检查-订单功能-20240601.md`、`代码检查-支付重构-20240601.md`。

## 审查文档生成要求

生成审查结果文档时，必须满足以下要求：

- 审查结论既要在会话中输出，也要同步写入 `.changes/review` 下的结果文件。
- 文档内容必须基于实际检查到的代码、测试和验证结果，禁止编造问题或验证结论。
- 如果未发现明确缺陷，也要生成审查文档，并写明“未发现具体缺陷”以及剩余风险。
- 文档中应尽量保留具体文件位置、问题级别、影响说明和修复建议，便于后续跟踪处理。

## 输出要求

输出时遵循以下规则：

- 先给 Findings，再给 Open Questions，最后给 Residual Risk。
- Findings 必须按严重程度排序。
- 每条 Findings 都要说明“问题是什么”“为什么重要”“建议怎么修”。
- 不要输出空泛评价，比如“代码还可以”“建议优化一下”。
- 如果没有发现明确问题，直接写明“未发现具体缺陷”。
- 若已生成审查文档，还应在结果中明确说明文档保存位置。

## 输出格式

请使用以下格式输出：

### Findings

1. [高] 问题描述。
   影响：说明该问题为什么重要，会导致什么后果。
   建议：给出最小可行修复方案。

2. [中] 问题描述。
   影响：说明该问题为什么重要，会导致什么后果。
   建议：给出最小可行修复方案。

### Open Questions

1. 仅记录会影响审查结论的前提假设或缺失上下文。

### Residual Risk

- 如果没有发现缺陷，说明剩余风险，例如测试未执行、环境未验证、异常路径未覆盖等。

## 审查时的具体要求

执行审查时，请遵循以下行为：

- 以代码审查视角工作，优先找 bug、风险、行为回归和缺失测试。
- 结论必须聚焦“当前改动是否安全可靠”。
- 尽量引用具体文件和位置。
- 如果问题成立条件依赖某个假设，需要明确写出假设。
- 不要把纯格式化问题当成主要结论。
- 不要为了显得全面而制造低价值问题。

## 示例输出

```md
Findings

1. [高] 更新逻辑缺少权限校验，导致已存在记录可被未授权用户修改。
   影响：会造成越权写入，属于实际安全问题。
   建议：在更新路径复用创建/删除路径中的权限校验逻辑。

2. [中] 异常处理分支记录了完整请求体，可能包含令牌或个人敏感信息。
   影响：敏感数据可能写入日志并长期保留。
   建议：仅记录必要字段，或在日志前进行脱敏处理。

Open Questions

1. 如果该接口只允许管理员访问，则第一个问题的严重程度可以下调，但仍建议保留校验。

Residual Risk

- 当前未看到异常分支的自动化测试，回归风险尚未完全收敛。
```

## 非目标

- 不主动重构与本次改动无关的模块。
- 不提出大范围架构改造，除非当前缺陷必须通过该方式修复。
- 不把格式、命名或个人风格偏好作为主要问题。
