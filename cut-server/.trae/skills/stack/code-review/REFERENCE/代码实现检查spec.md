# 代码实现检查规范

## 具体要求

1. Spec 需求文档优先：如果有目标需求分析后的 spec.md 文档，则以 spec.md 文档为基准。
2. 代码分析范围：分析当前分支自创建以来未提交的改动，以及已提交的、排除 merge 提交之外的所有改动。
3. 功能逻辑：
	- 一致性：检查代码实现是否与需求功能逻辑一致，是否满足需求功能和技术实现要求。
	- 完整度：检查代码实现是否完整，是否存在待完善的功能逻辑。
	- 充分性：检查是否遗漏某些业务规则细节，边界条件是否考虑充分等。
4. 代码设计：
	- 可读性：保持代码的可读性，避免使用奇技淫巧，避免过度设计。
	- 可扩展性：代码是否方便扩展，容易持续迭代，避免强耦合。
	- 重复性：遵守 Don't Repeat Yourself 原则，复用已有代码，在职责单一的前提下尽量减少重复代码的编写。
	- 可维护性：代码的可维护性由多个因素共同决定。代码可读性好、简洁、可扩展性好，会更易于维护。
	- 可测性：代码可测试性的好坏，同样可以反映代码质量的高低；可测试性差会导致单元测试难以编写。
5. 代码质量：
	- 安全问题：是否存在安全隐患，例如 SQL 注入、CSRF、越权等安全漏洞。
	- 性能问题：是否会产生性能损害，例如慢 SQL、热点 key、数据倾斜等问题。
	- 资损问题：是否存在资损风险，例如金额计算错误、数据重复写入等问题。
	- 并发问题：是否存在并发问题，例如数据重复写入、数据丢失等问题。
	- 数据一致性：是否存在数据不一致问题，例如缺少事务约束导致数据不一致等。
	- 线上风险：是否会对稳定性产生潜在影响，例如死锁、死循环、NPE、Full GC、OOM 等问题。
	- 未知影响：是否会对用户体验产生潜在影响，例如某个 Feature 上线后潜在影响其他功能表现等。
6. 代码规范：
	- 是否符合当前工程统一的代码风格要求以及分层次的代码规范要求。
