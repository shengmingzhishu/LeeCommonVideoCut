# 任务拆分

## 技能目标

当用户已经完成需求分析和设计方案，需要把改动点进一步落成可执行研发任务时，使用本技能。

本技能面向 Python 项目的服务变更，目标是把需求和设计中的模块改动点收敛为清晰、分组明确、可直接执行的编码任务文档，供开发、联调、测试或 AI 编码工具继续使用。

## 参考规范

本技能依赖当前目录下的规范文件：

- `REFERENCE/任务拆分spec.md`：Python 项目任务拆分文档的编写规范与模板。

## 适用场景

- 已完成需求分析文档和设计文档，需要继续生成研发任务清单。
- 需要把模块改动点转化为 API、Service、Repository、Schema、配置、测试等交付任务。
- 需要为开发排期、AI 编码执行或代码评审准备统一任务输入。

## 输入要求

执行本技能时，优先收集以下信息：

- 本次需求分析文档的位置。
- 本次设计文档的位置。
- 需求名称、变更类型、目标日期。
- 已识别出的模块改动点、接口改动点、数据改动点和风险点。
- 当前 Python 项目的核心目录、模块职责和可复用能力。

如果需求分析文档或设计文档缺失，或改动点尚未明确，不允许直接编造任务，应先列出待确认项，再进行任务拆分。

## 工作流程

### 1. 确认输入材料

- 优先读取需求分析文档和设计文档。
- 提取其中的模块改动点、交付物、兼容性约束和待确认事项。
- 结合代码库确认已有模块、已有接口和可复用实现，避免输出脱离代码结构的任务。

### 2. 创建任务拆分产物目录

在当前项目根目录下按以下规则组织产物：

1. 若不存在 `.changes` 目录，则创建 `.changes`。
2. 在 `.changes` 下创建本次需求的子目录，命名格式为 `${变更类型}-${需求名称}-${当前日期}`。
3. 示例：`新增-订单功能-20240601`。

### 3. 生成任务拆分文档

- 使用 `REFERENCE/任务拆分spec.md` 作为模板。
- 任务拆分文档保存到对应变更子目录下，命名格式为 `任务拆分-${需求名称}.md`。
- 文档必须覆盖需求分析文档和设计文档中的全部模块改动点；若某模块对当前 Python 服务不适用，需明确写出不适用原因。

### 4. 控制拆分粒度

任务拆分应满足以下要求：

- 任务必须能映射到明确交付物，如 Router、Schema、Service、Repository、脚本、测试、文档或配置。
- 任务粒度足够让开发人员或 AI 工具直接执行，但不能粗到“完成后端开发”，也不能细碎到逐行编码。
- 优先描述“扩展已有能力”或“复用接入已有模块”，仅在确有依据时输出新增任务。

### 5. 面向 Python 项目的拆分约束

编写任务时，必须结合 Python 项目的实现特点：

- 区分路由层、应用服务层、领域逻辑层、持久化层、异步任务层和公共能力层。
- 明确涉及的交付物类型，如 Pydantic Model、ORM Model、Repository、Celery 任务、配置项、pytest 用例等。
- 测试任务应优先贴合项目现有测试体系，不默认引入新的测试框架。
- 若需求未涉及数据库、异步任务、配置或运维配套，不得强行补出对应任务分类。

## 输出要求

输出结果至少包括以下内容：

- 任务拆分文档摘要。
- 主要任务分类及每类关键交付物摘要。
- 复用点、扩展点和新增点的结论。
- 待确认任务或前置条件。
- 任务拆分文档保存位置。

## 执行约束

- 严格依据需求分析文档、设计文档和真实代码结构输出任务。
- 不得输出没有交付物指向的泛化建议。
- 不得把需求分析全文或设计全文重复粘贴为任务内容。
- 任务拆分要兼顾开发实施、测试验证、发布准备和回滚准备。

## 推荐输出格式

建议按以下顺序给出结果：

1. 任务拆分范围与前提。
2. 任务分类摘要。
3. 关键任务列表。
4. 待确认事项。
5. 文档保存位置。

## 非目标

- 不输出脱离当前代码结构的理想化任务清单。
- 不把抽象建议、重构想法或产品描述当成研发任务。
- 不在信息不完整时伪造确定性任务。
