# Python 服务变更设计规范（极简版）

本文档用于指导生成 Python 项目的服务变更设计文档。目标是在保证可落地性的前提下，用最少章节覆盖服务设计所需的关键信息。

## 1. 文档定位

- 输入：本次需求分析文档、相关代码实现、已有接口和数据结构。
- 输出：可直接指导开发、联调、测试和评审的设计文档。
- 适用对象：Python 后端服务、定时任务、脚本任务、公共包或工具类变更。

## 2. 产物目录

在当前项目根目录下按以下规则组织产物：

1. 若不存在 `.changes` 目录，则创建 `.changes`。
2. 在 `.changes` 下创建本次需求的子目录，命名格式为 `${变更类型}-${需求名称}-${当前日期}`。
3. 示例：`修改-订单状态同步-20260520`。

## 3. 设计文档命名

生成的设计文档保存到对应变更子目录下，命名格式为 `设计文档-${需求名称}.md`。

## 4. 设计文档最小章节

合理划分设计模块，针对每个模块编写设计，对于每个模块设计输出至少包含以下章节；如果某章节不适用，必须写明原因，不能直接省略。

### 4.1 需求与变更分析

说明本次需求想解决什么问题，以及为什么需要改动现有服务。

至少覆盖：

- 需求背景与业务目标。
- 当前实现现状和痛点。
- 本次变更是新增、修改还是删除。
- 影响范围概览，包括上下游服务、任务或外部系统。

### 4.2 变更范围分析

从实现角度说明本次会改哪些模块，以及每个模块承担什么职责。

至少覆盖：

- 服务或模块变更：如 router、service、model、repository、task、common。
- 接口变更：外部接口、内部接口、异步任务入口。
- 数据结构变更：请求体、响应体、ORM 模型、消息体、缓存结构、日志结构。
- 不改动的部分：明确哪些模块复用现有能力，不在本次范围内。

### 4.3 后端变更设计

这是核心章节，按最小可落地原则写清处理链路。

至少覆盖：

- 入口：请求入口、任务入口或脚本入口。
- 处理流程：核心步骤、调用关系、关键分支、异常路径。
- 输出：返回结果、落库结果、消息投递或状态变更。
- 兼容性：对老接口、老数据、老调用方是否兼容。

建议优先用简洁文字描述；确有必要时补充流程图或时序图。

### 4.4 接口设计

说明接口是否有变化，以及变化点。

至少覆盖：

- 接口名称、调用方向和用途。
- 请求参数、响应字段、错误码是否变化。
- 认证鉴权、幂等、超时、重试等约束。
- 若无接口变化，写明从技术层面为何无变化。

### 4.5 数据设计

说明本次变更引起的数据层设计变化。

至少覆盖：

- 数据模型或 Schema 是否变化。
- 数据库存储、缓存、文件、消息体、日志结构是否变化。
- 数据兼容方式：默认值、迁移策略、老数据处理。
- 若无数据变化，写明原因。

### 4.6 配置设计

说明服务配置是否变化。

至少覆盖：

- 新增或修改的配置项。
- 配置类型：业务类、开关类、系统类。
- 配置存储位置：环境变量、配置文件、配置中心、数据库。
- 配置生效方式、默认值、回滚策略。
- 若无配置变化，写明原因。

### 4.7 测试与风险

说明如何验证本次设计，以及主要风险点。

至少覆盖：

- 单元测试、集成测试、接口测试或回归测试范围。
- 关键异常场景和边界场景。
- 发布影响、灰度方式、回滚方案。
- 依赖风险、性能风险、兼容性风险和待确认事项。

## 5. Python 项目专项要求

面向 Python 项目输出设计时，应尽量明确以下内容：

- Web 框架层：FastAPI/Flask/Django 路由或视图的改动点。
- 数据模型层：Pydantic、dataclass、ORM Model、Serializer 的改动点。
- 业务服务层：service、manager、domain、usecase 等核心逻辑变更。
- 持久化层：repository、DAO、SQL、缓存读写、消息发布。
- 异步能力：Celery、APScheduler、消息消费、后台任务。
- 工程能力：日志、监控、鉴权、配置、异常处理、测试目录。

## 6. 编写原则

- 先写事实，再写方案；所有方案都要能回到需求和代码依据。
- 只保留对实现有帮助的信息，不写空泛原则。
- 优先复用现有模块和能力，避免默认新增复杂抽象。
- 对“不适用”章节必须给出明确技术原因。

## 7. 极简模板

可直接按以下结构生成设计文档：

```md
# 设计文档-${需求名称}

## 1. 需求与变更分析
### 1.1 需求背景
### 1.2 当前现状
### 1.3 本次变更目标

## 2. 变更范围分析
### 2.1 涉及模块
### 2.2 涉及接口
### 2.3 涉及数据结构
### 2.4 非本次范围

## 3. 后端变更设计
### 3.1 总体处理流程
### 3.2 模块设计
### 3.3 异常与兼容设计

## 4. 接口设计
### 4.1 变更接口
### 4.2 无变化说明（如无）

## 5. 数据设计
### 5.1 数据模型变化
### 5.2 存储与兼容设计

## 6. 配置设计
### 6.1 配置项变化
### 6.2 生效与回滚

## 7. 测试与风险
### 7.1 测试方案
### 7.2 发布与回滚
### 7.3 风险与待确认事项
```
