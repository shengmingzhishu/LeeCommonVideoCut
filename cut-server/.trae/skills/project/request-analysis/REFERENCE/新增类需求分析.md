> 本模板适用于后端研发的新增类型需求文档(PRD)分析和设计，旨在规范从0到1新增功能的需求分析和技术方案输出质量。

# 任务目标
根据用户输入的新增需求，结合当前代码库的领域模型、公共能力和相邻业务链路，产出可落地实施的技术方案文档，以便用于AI理解和编码。

# 任务清单
1. 需求分析: 根据用户需求，明确新增功能的业务目标、核心流程、适用范围、边界条件和成功标准。
2. 代码分析: 根据需求分析，结合当前代码库，搜索可复用的领域模型、公共组件、基础设施和相似业务链路，分析系统接入方式，并使用 mermaid 语法输出新增功能时序图或流程图。
3. 新增点分析: 结合需求分析和代码分析，列出新增功能所需的数据结构、接口协议、服务流程、配置项、任务链路等详细代码改动点。
4. 影响分析: 分析和评估新增能力对现有业务、上下游依赖、部署运维、监控告警、权限控制等方面的影响和风险。
5. 生成技术方案: 综合以上分析结果生成可落地实施的技术方案文档。

## 具体要求
1. 需求分析要求:
    * 优先识别新增需求属于全新能力、现有能力扩展还是新场景接入，明确业务边界，不得将“新增”误判为“修改同语义老功能”。
    * 必须拆清楚新增功能的输入、处理、输出、异常、约束、幂等、权限、状态流转和对外可见行为。
2. 代码分析要求:
    * 先根据需求分析找到所有相关入口代码，包括 API、消息消费、定时任务、内部服务调用、配置开关等，再从入口开始分析完整链路。
    * 重点识别可复用的领域对象、校验逻辑、持久化层、通用组件、公共 SDK、基础能力和相似流程，避免重复建设。
    * 若当前代码库不存在完全可复用实现，需要明确指出必须新增的模块、类、接口、表结构或配置，并说明原因。
3. 新增点分析要求:
    * 遵守最大化复用原则，优先复用已有代码和接口协议；仅在业务语义不同、职责边界不一致或扩展成本过高时新增实现。
    * 对每个新增点都要说明新增原因、所属模块、上下游依赖、核心职责和与现有能力的关系。
    * 对需要新增的数据结构、数据库表/字段、枚举、配置、任务、消息体、接口入参与出参，必须逐项列清楚。
4. 技术方案设计要求:
    * 必须遵守最大化复用、最小化新增原则: 不要轻易增加接口协议、服务分层和数据结构，禁止出现语义重复或结构高度雷同的实现。
    * 高内聚、低耦合原则: 新增功能应有清晰边界，职责合理拆分，便于后续扩展和维护。
    * 向后兼容原则: 所有新增改动必须与已有功能兼容，不能影响与本次需求无关的业务链路。
    * 可观测性原则: 对新增链路需补充必要的日志、监控、告警、埋点和审计能力。
    * 测试用例: 包括功能测试、非功能测试(如性能、可靠性、兼容性、回滚验证等)。测试覆盖要包含正常流程、异常流程、边界条件和灰度场景。
5. 输出要求:
    * 严格根据用户输入的需求和代码分析结果进行分析，禁止编造不存在的业务规则、系统能力或代码实现。
    * 先描述分析过程和结论，再使用中文生成符合要求的技术方案。
    * 技术方案中应明确区分“可复用部分”和“必须新增部分”。

## 技术方案建议章节
1. 需求背景
2. 需求分析
3. 现状代码分析
4. 新增功能流程设计
5. 详细改动点设计
6. 数据与接口设计
7. 影响与风险分析
8. 测试方案
9. 待决议列表
