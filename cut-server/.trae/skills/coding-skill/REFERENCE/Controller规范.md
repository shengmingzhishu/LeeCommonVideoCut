# Controller 规范

## 适用范围

- 本规范适用于 Python 后端项目中的 Controller 层代码，包括但不限于 Web 框架中的路由处理函数、视图函数、接口处理器、Router 层封装等。
- 如果项目中未明确使用 Controller 命名，也适用于承担 HTTP 请求接入职责的 Handler、View、Endpoint 等同类代码。

## 1. 职责定位

- Controller 层只负责请求接入与响应返回，不承载核心业务逻辑。
- Controller 层应聚焦以下职责：
	- 路由定义与接口暴露。
	- 请求参数接收、解析与基础校验。
	- 身份识别、权限校验、幂等校验等接入层控制。
	- 调用 Service / Domain 层完成业务编排。
	- 统一响应封装与错误返回。
- 禁止在 Controller 中直接编写复杂业务规则、数据库访问、跨模块数据拼装等逻辑。

## 2. 设计要求

- 保持 Controller 轻量化，单个接口方法应做到职责单一、逻辑清晰。
- 优先复用已有的请求模型、响应模型、鉴权组件、异常处理组件和通用工具方法，避免重复实现。
- 当一个接口流程包含多步业务判断时，应下沉到 Service 层实现，Controller 只保留必要的调用顺序和入出参处理。
- 同一类资源的接口建议集中放在同一个 Controller 或 Router 中，避免接口分散导致维护困难。
- Controller 命名应体现业务语义，避免使用无意义缩写。

## 3. 路由与接口定义

- 路由路径应语义化，优先使用名词表达资源，避免路径中出现实现细节。
- HTTP 方法应与业务动作匹配：
	- 查询类接口优先使用 GET。
	- 新增类接口优先使用 POST。
	- 更新类接口优先使用 PUT 或 PATCH。
	- 删除类接口优先使用 DELETE。
- 路由定义应保持风格统一，避免同一模块同时出现多套路径命名风格。
- 接口版本控制、模块前缀、统一前缀等约定应遵循项目现有规范。

## 4. 入参与出参规范

- 所有接口方法必须显式声明参数含义，优先使用类型注解。
- 入参超过 3 个或结构明显复杂时，应封装为请求对象，避免参数平铺。
- 请求对象、响应对象优先复用框架或项目中已有的模型定义方式，例如 Pydantic Model、dataclass 或项目统一 DTO。
- 禁止直接透传未经校验的原始字典到业务层。
- 出参必须具备明确语义，避免返回结构不稳定的裸字典或无意义的空值。
- 响应结构应遵循项目统一约定，成功和失败响应格式保持一致。

## 5. 参数校验

- 参数校验优先放在 Controller 层完成，至少覆盖必填项、类型、长度、格式、枚举值和基础边界条件。
- 复杂业务规则校验应放到 Service / Domain 层，不应全部堆积在 Controller 中。
- 对于路径参数、查询参数、请求体参数，应分别进行清晰校验，避免混用。
- 校验失败时应返回明确、可理解的错误信息，不应暴露内部实现细节。

## 6. 异常处理

- Controller 层应优先复用项目统一异常处理机制，例如全局异常拦截器、中间件或异常转换器。
- 禁止在每个接口中重复编写大量 try-except 逻辑；仅在需要补充上下文信息或转换异常语义时局部捕获。
- 业务异常与系统异常应明确区分：
	- 业务异常返回可理解、可预期的错误码和错误信息。
	- 系统异常避免直接暴露堆栈、SQL、内部路径等敏感信息。
- 对外返回的错误码、错误信息应符合项目统一规范。

## 7. 安全要求

- 必须根据接口场景接入身份认证、权限校验、租户隔离或数据范围校验。
- 对外部输入统一做合法性校验，避免 SQL 注入、命令注入、路径穿越、反序列化风险等安全问题。
- 涉及敏感信息的接口应避免在日志和响应中泄露明文数据，例如手机号、身份证号、令牌、密钥等。
- 对需要防重、幂等控制的接口，应结合业务语义接入幂等机制。

## 8. 日志与可观测性

- Controller 层日志应记录必要的请求上下文，例如请求标识、核心业务标识、调用结果和异常摘要。
- 禁止无差别打印完整请求体、响应体和敏感字段。
- 日志内容应便于问题定位，但避免冗余和噪声。
- 对关键接口可补充耗时统计、调用次数、失败次数等监控埋点。

## 9. 编码规范

- 必须遵循项目统一的 Python 编码规范，包括命名、缩进、导入顺序、换行和模块划分。
- 函数名、变量名、类名应具有明确业务语义。
- 所有 Controller 方法应补充必要的文档注释或 docstring，说明接口用途、关键参数和返回含义。
- 复杂分支、兼容逻辑或特殊约束应使用简洁注释说明原因，而不是解释表面代码行为。
- 禁止在 Controller 中出现难以测试的隐藏状态或强耦合调用。

## 10. 质量要求

- Controller 层代码应具备良好的可读性、可维护性和可测试性。
- 新增或修改接口时，应至少覆盖以下测试场景：
	- 正常请求场景。
	- 参数缺失或参数非法场景。
	- 权限不足或未认证场景。
	- 业务异常场景。
	- 边界条件场景。
- 接口改动应向后兼容已有调用方；如果存在不兼容变更，必须明确版本策略或迁移方案。

## 11. 禁止事项

- 禁止在 Controller 中直接操作数据库。
- 禁止在 Controller 中堆积大段业务判断和数据转换逻辑。
- 禁止复制粘贴相同的参数解析、异常处理和响应封装代码。
- 禁止返回不稳定、无文档约束的响应结构。
- 禁止将内部异常原样暴露给前端或调用方。
