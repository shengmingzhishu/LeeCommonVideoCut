# 服务变更设计

## 技能目标

当用户已经有明确需求，且需要把需求进一步收敛成可执行的后端设计方案时，使用本技能。

本技能面向 Python 项目中的服务类变更，目标是在不过度设计的前提下，输出一份结构清晰、章节精简、可以直接指导开发和评审的设计文档。

## 参考规范

本技能依赖当前目录下的规范文件：

- `REFERENCE/设计规范spec.md`：Python 服务变更设计文档的极简模板与编写规则。

## 适用场景

- 已有需求分析文档，需要继续生成设计文档。
- 需要为 Python 服务的新增、修改、删除类需求编写设计方案。
- 需要把代码链路、接口变化、数据变化和测试方案整理成统一文档。
- 需要为开发、联调、测试或评审提供实现依据。

## 输入要求

执行本技能时，优先收集以下信息：

- 本次需求分析文档的位置。
- 需求名称、变更类型、目标日期。
- 受影响的 Python 服务、模块、包、脚本或任务。
- 已有接口、数据模型、配置项和部署方式。
- 关键约束，如兼容性、性能、灰度、回滚、依赖系统。

如果需求分析文档缺失，或代码库中找不到关键实现入口，需要先说明缺口，再输出最小可确认版本，禁止编造不存在的服务能力。

## 工作流程

### 1. 确认输入材料

- 优先读取对应需求分析文档。
- 从需求分析文档中提取每一条需求、变更背景、边界和待确认项。
- 结合代码库确认服务入口、核心模块、外部依赖和可复用能力。

### 2. 创建设计产物目录

在当前项目根目录下按以下规则组织产物：

1. 若不存在 `.changes` 目录，则创建 `.changes`。
2. 在 `.changes` 下创建本次需求的子目录，命名格式为 `${变更类型}-${需求名称}-${当前日期}`。
3. 示例：`新增-订单功能-20240601`。

### 3. 生成设计文档

- 使用 `REFERENCE/设计规范spec.md` 作为模板。
- 设计文档保存到对应变更子目录下，命名格式为 `设计文档-${需求名称}.md`。
- 文档必须覆盖需求分析文档中的全部章节；若某章节对当前 Python 服务不适用，需明确写出不适用原因。

### 4. 控制设计粒度

本技能默认输出极简设计，不追求大而全。设计内容应优先覆盖以下最小集合：

- 需求和变更分析。
- 变更范围分析。
- 后端变更设计。
- 接口设计。
- 数据设计。
- 配置设计。
- 测试与风险说明。

仅当需求确实涉及页面或交互时，才补充界面设计。

### 5. 面向 Python 项目的设计约束

编写设计时，必须结合 Python 项目的实现特点：

- 明确变更位于 API 层、应用服务层、领域逻辑层、仓储层、任务调度层或公共库。
- 明确涉及的框架能力，如 FastAPI、Flask、Django、Celery、SQLAlchemy、Pydantic 等。
- 明确输入输出模型、异常处理、日志埋点、配置来源和测试策略。
- 优先复用现有模块、Schema、DAO、任务或中间件，不默认新增重复抽象。

## 输出要求

输出结果至少包括以下内容：

- 设计文档摘要。
- 关键模块与主要改动点摘要。
- 接口、数据、配置是否变更的结论。
- 主要风险、兼容性影响和待确认事项。
- 设计文档保存位置。

## 执行约束

- 严格基于需求分析文档和真实代码实现输出设计。
- 不得把需求分析中未出现、代码中也无依据的业务规则写成既定方案。
- 设计应能指导开发落地，避免只写原则性空话。
- 极简不等于遗漏，必须覆盖实现、测试、发布风险所需的最小信息。

## 推荐输出格式

建议按以下顺序给出结果：

1. 设计范围与前提。
2. 模块改动设计。
3. 接口与数据变更。
4. 配置、测试与风险。
5. 文档保存位置。

## 非目标

- 不在信息不足时虚构数据库表结构、接口字段或业务流程。
- 不默认输出厚重架构文档。
- 不把与本次需求无关的重构内容纳入设计范围。
