# 开发工作流（共享层）

> 本规范适用于所有项目，前后端通用。技术栈特定的规则在各技术栈层规则中定义。

## 1. 零干预开发流程

> 目标：用户仅在项目启动时填写一次初始化问卷，后续由 AI 自主驱动开发、自追踪、自验证，实现零人员干预。

### 1.1 项目启动流程

```
用户填写问卷 → AI 读取问卷+参考资料 → AI 生成项目上下文 → AI 生成 plan 骨架 → AI 自主开发
```

1. **用户填写 `plan/00-项目初始化问卷.md`**（唯一需要人工的步骤）
   - 模板见 `.trae/rules/templates/00-项目初始化问卷.md`
   - 填写技术选型、业务功能、参考资料路径、自主决策授权等
   - 不确定的项可填"由 AI 决策"

2. **AI 读取问卷并生成项目上下文**
   - 读取问卷全部内容
   - 如有参考项目目录，读取学习其架构和风格
   - 如有设计文档目录，提取功能点
   - 如有后端 API 文档（OpenAPI/Swagger），提取接口清单与数据模型
   - 生成 `plan/00-项目上下文.md`（规范见本文 §8）

3. **AI 生成 plan 目录骨架**
   - 根据 `00-项目上下文.md` 的功能点清单，初始化各方向文件
   - `02-任务列表.md` 生成任务拆分
   - `01-开发进度.md` 生成里程碑
   - `07-需求对应.md` 生成需求映射表

4. **AI 自主驱动开发**
   - 每次工作前读取 `00-项目上下文.md` 功能点清单
   - 找到第一个非 `done` 的功能点，按状态执行对应动作
   - 完成后更新状态，同步更新相关 plan 文件
   - 遇到不确定时按自主决策规则处理，不暂停等待人工

### 1.2 功能点状态驱动

| 当前状态 | AI 执行动作 | 完成后切换 | 同步更新 |
|---------|-----------|-----------|---------|
| pending | 设计方案，拆解任务 | → designing | 02-任务列表, 01-开发进度 |
| designing | 编写代码实现 | → developing | 08-代码日志, 04-接口文档 |
| developing | 编写并执行单元测试 | → testing | 05-单元测试 |
| testing | 功能验证，更新映射 | → done | 06-功能测试, 07-需求对应 |

### 1.3 自主决策规则

AI 遇到不确定情况时，按以下优先级处理，**不暂停等待人工**：

1. 查阅 `00-项目上下文.md` 已有决策记录
2. 查阅 `.trae/rules/` 规则约束
3. 查阅问卷提供的参考资料
4. 按最佳实践自主决策，记录到 `03-问题记录.md`（含背景、决策、依据、影响）
5. 继续执行

### 1.4 检查点自验证

| 检查点 | 验证内容 | 不通过时 |
|--------|---------|---------|
| 设计完成 | 任务拆解完整、无遗漏功能点 | 补充任务后继续 |
| 编码完成 | 代码符合规范、构建通过、类型检查无错误 | 修复后继续 |
| 单测完成 | 覆盖率达标、所有用例通过 | 补充用例后继续 |
| 功能完成 | 需求对应表全部标记完成 | 回到未完成项继续 |

### 1.5 轻量模式 vs 完整模式

按变更性质分类：

| 变更类型 | 模式 | 典型场景 |
|---------|------|---------|
| Bug 修复 | 轻量 | 报错修复、样式修正 |
| 代码质量 | 轻量 | 格式化、补充注释 |
| 重构 | 轻量 | 重命名、提取函数/组件 |
| 配置调整 | 轻量 | 修改超时、调整日志级别 |
| 新功能 | **完整** | 新增页面、新增接口、新增业务流程 |
| 数据库变更 | **完整** | 新增表、新增字段、数据迁移 |
| 架构调整 | **完整** | 新增分层、改变数据流向 |
| 依赖变更 | **完整** | 新增/升级/替换依赖包 |
| 跨模块逻辑 | **完整** | 修改涉及 3 个以上模块 |

轻量模式：直接编码 + 自验证 + 卡点检测，仅更新 `08-代码日志.md`
完整模式：完整零干预流程，更新全部相关 plan 文件

## 2. 项目目录规范

### 2.1 /docs 目录（需求设计文档）

- 每个独立功能模块对应一个文档
- 文档命名：`docs/<模块名>_<需求简称>.md`
- 文档内容：需求背景、方案设计、接口定义/依赖、验收标准
- 禁止放入临时笔记、会议纪要

### 2.2 /plan 目录（项目计划与过程文档）

| 编号 | 文件名 | 方向 | 职责 |
|------|--------|------|------|
| 00 | `00-项目初始化问卷.md` | 初始化问卷 | 用户唯一需填写的文件 |
| 00 | `00-项目上下文.md` | 项目上下文 | AI 自动生成的第一读取文件 |
| 01 | `01-开发进度.md` | 开发进度 | 阶段、里程碑、阻塞项 |
| 02 | `02-任务列表.md` | 任务拆解 | 任务清单、状态、优先级 |
| 03 | `03-问题记录.md` | 问题记录 | 问题、自主决策记录 |
| 04 | `04-接口文档.md` | 接口文档 | API 定义、变更记录 |
| 05 | `05-单元测试.md` | 单元测试 | 覆盖计划、用例、结果 |
| 06 | `06-功能测试.md` | 功能测试 | 验收用例、测试结果 |
| 07 | `07-需求对应.md` | 需求对应 | 需求→代码→测试映射 |
| 08 | `08-代码日志.md` | 代码日志 | 变更摘要、提交记录 |

### 2.3 /tests 目录

- 测试文件分类存放（unit/integration/api/e2e）
- 测试输出按「日期+时间戳」文件夹独立存放

### 2.4 通用目录结构

```
项目根目录/
├── docs/                        # 需求设计文档
├── plan/                        # 项目计划与过程文档
├── tests/                       # 测试文件
│   ├── unit/
│   ├── integration/
│   ├── e2e/
│   └── output/
├── logs/                        # 运行日志
├── src/                         # 源代码
└── resources/                   # 环境配置文件
```

## 3. 文档规范

### 3.1 必须更新文档的场景

- 新增公共 API / 组件
- 修改公共 API 签名 / 组件 Props
- 新增配置项
- 修改部署流程
- 新增依赖库
- 架构调整

## 4. 问题排查

### 4.1 遇到问题时

1. 先查看日志，通过 traceId/事务 ID 定位完整调用链路
2. 检查配置是否正确
3. 复现问题，确认触发条件
4. 搜索 Issue / FAQ 是否有同类问题
5. 最小化复现场景
6. 无法解决时附上：错误堆栈、traceId、复现步骤、环境信息

## 5. 卡点检测与恢复机制

> 本节强制生效。AI 在开发过程中必须持续自检是否陷入卡点。

### 5.1 卡点检测

| 条件 | 阈值 |
|------|------|
| 同一文件修改次数 | ≥ 3 次 |
| 同一错误类型出现 | ≥ 2 次 |
| 同一问题对话轮次 | ≥ 5 轮 |
| 修复后测试仍失败 | ≥ 2 次 |
| 回滚或重做同一改动 | ≥ 2 次 |

### 5.2 恢复流程

```
检测到卡点 → 停止修复 → 汇总失败记录 → 生成验证方案 → 方案评审 → 执行修复 → 多维度验证 → 通过则继续
```

### 5.3 验证手段选择策略

| 问题类型 | 首选验证手段 |
|---------|------------|
| 纯逻辑错误 | 单元测试 |
| API 问题 | 程序运行 + 接口调用 |
| UI 渲染问题 | 浏览器截图对比 |
| 交互问题 | 浏览器模拟操作 |
| 数据流问题 | 程序运行 + 数据状态检查 |

### 5.4 卡点升级

恢复流程执行 1 轮后仍未解决：
1. 执行回滚（保存 diff → 回滚代码 → 验证恢复）
2. 升级为严重卡点，跳过当前问题
3. 标记为 blocked，继续下一个功能点

### 5.5 规则执行优先级

- 检测到卡点 → 立即中断当前操作 → 执行恢复流程
- 恢复流程未完成 → 不允许开始新的功能点开发
- 验证方案未通过 → 不允许标记问题已解决
