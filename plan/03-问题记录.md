## Q17：刷新后如何进入成片完成页；TTS「完成」如何判定
- **背景**：完成页 `showComplete` 是会话内状态，刷新后即使已有成片也看不到预览/下载入口；另外 pyttsx3 在长文本下会静默产出 566 字节空音频，但任务仍标记 completed，Step3 会拿到无效音频
- **决策**：① 已成片时在步骤区顶部显示「已有 N 个成片 / 查看成片」，由用户点击进入完成页，不自动跳转（避免打断继续编辑）；② 每个 TTS 引擎产出后统一用 ffprobe 校验时长，`<=0.5s` 视为无效并降级到下一引擎
- **依据**：出口可达性优先，同时保持编辑上下文；TTS 任务状态必须以产物可播放为准，而非函数返回
- **影响**：`CreationWizardPage.tsx` 增加成片入口；`tts_manager.py` 新增 `_probe_duration()`，默认链路 edge-tts（403）→ pyttsx3（有效 56.885s）

## Q16：成片预览/下载的路径与鉴权方式
- **背景**：需求建议 `GET /api/outputs/{output_id}/download`；但 `outputs` 表仅按 creation 归属，单凭 output_id 仍需额外查询 creation 才能鉴权
- **决策**：采用嵌套资源路径 `GET /api/creations/{creation_id}/outputs/{output_id}/file`，`download=true` 时附件下载、默认 inline；鉴权、所有权、`workdir` 路径穿越在一次请求内完成
- **依据**：REST 资源层级更清晰；避免为 output 单独新增全局路由与重复归属查询
- **影响**：契约 Outputs Tag 操作数 1→2；前端 `OUTPUTS.FILE` 使用带 Bearer 的 blob 请求，而非 `<video src>` 直链

## Q15：视频上传单文件 vs 多文件、预览方式
- **背景**：产品入口需要用户「选择一个本地视频」；现有文件接口支持一次一个文件，项目素材是按目录扫描
- **决策**：入口按单文件设计（`maxCount=1`）；服务端用文件所在目录作为 `project.video_dir`，多文件能力通过多次上传到同一目录保留；预览用内联 `<video>`（blob + Bearer），下载用 `attachment`
- **依据**：最短可用路径 + 现有 `VideoMarkerManager.scan(video_dir)` 目录扫描模型
- **影响**：`ProjectCreate/Update` 新增 `video_file_ids`；上传后 `project.video_dir` 为服务端绝对路径；服务器路径输入保留为高级选项

## Q11：后端错误响应恒 HTTP 200，导致前端 401 跳转失效
- **背景**：所有业务异常 `http_status=200`，而前端 `request.ts` 靠 `status === 401` 触发清登录态 + 跳登录页，条件永不满足；契约也声明的是标准 401/402/403/422
- **决策**：异常类改为语义化 HTTP 状态码（401/402/403/404/422/400/502），错误响应字段统一为 `message`（对齐契约 `ErrorResponse`）
- **依据**：跨端协作约定 §2 + 契约 `ErrorResponse` 定义 + 前端拦截器实现
- **影响**：`exceptions.py` 全部异常类 + `main.py` 全局处理器；新增 `RequestValidationError`（422）与 `Exception`（500）兜底

## Q12：traceId 只在响应头，响应体恒为 null
- **背景**：`health.py` 注释写"中间件会回填"，但 `trace.py` 只写 `X-Trace-Id` 响应头；跨端约定 §9 要求前后端日志都能对齐
- **决策**：中间件在 JSON 响应体中回填 `traceId` 字段（已有值不覆盖）
- **依据**：跨端协作约定 §9「后端响应：通过 X-Trace-Id 响应头回写」+ 前端 `ApiResponse.traceId` 类型定义
- **影响**：`core/trace.py` 重写（新增 `_fill_trace_id` + 字节流重建）
