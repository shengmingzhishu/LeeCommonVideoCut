> 本模板适用于后端研发的修改类型需求文档（PRD）分析和设计，旨在规范需求分析和方案设计的内容质量。

# 任务目标

根据用户输入的需求，结合当前代码库相关功能分析，产出技术方案文档，以便用于 AI 理解和编码。

# 任务清单

1. 需求分析：根据用户需求，充分理解并分析需求功能以及需求改动点。
2. 代码分析：根据需求分析，结合当前代码库，搜索相关代码，分析并理解相关业务逻辑，再使用 Mermaid 语法生成相关图示。
3. 改动点分析：结合需求分析和代码分析，列出详细的代码改动点。
4. 影响分析：分析和评估代码改动对现有业务逻辑的影响和风险。
5. 生成技术方案：综合以上分析结果生成可落地实施的技术方案文档。

## 具体要求

1. 代码分析要求：
   - 先根据需求分析找到所有相关入口代码，从入口代码开始分析整个链路，找出所有的代码改动点。
2. 改动点分析要求：
   - 遵守代码复用原则，尽量复用已有代码和接口协议（不同业务语义的代码不能复用）。
   - 例如：在一次索赔基础之上增加二次索赔功能，发起索赔链路相同。这种情况就不需要新增发起索赔的接口方法协议。
3. 技术方案设计要求：
   - 必须遵守最大化复用、最小化改动原则：不要轻易增加接口协议，禁止重复代码和数据结构高度雷同、平铺。
   - 高内聚、低耦合原则：不同业务语义的代码不能复用，系统内部方法合理拆分，易修改、易维护。
   - 向后兼容原则：所有改动必须向后兼容已有功能，不能影响与需求改动无关的功能。
   - 测试用例：包括功能测试、非功能测试（比如性能测试、兼容性测试、可靠性测试等）。用例覆盖要全面，不同测试场景都需要覆盖。
4. 严格根据用户输入的需求进行分析，禁止编造不存在的内容。
5. 先描述分析的内容，再使用中文生成符合要求的技术方案。

## 待决议列表

- 不知道或者有争议的内容部分不要瞎编，使用待办列表留给人工确认，代办项格式：`[序号]、[具体内容]`。
- 当某项待办澄清后，把相关待办项设置为 `- [x]`，不要删除。
- 待决议列表必须放在技术方案的最后一个章节。
