# 设计文档驱动代码补全

基于指定设计文档完成代码补全，并强制执行“先规划、分步实现、逐步单测验证、完成后总结”的闭环。

## 何时使用

当用户有以下意图时使用此技能：
- 根据设计文档补全现有代码
- 按需求文档或设计说明逐步实现功能
- 先看测试再规划开发步骤
- 每写完一部分代码就先验证，再继续下一步
- 需要在开发完成后产出总结报告

典型触发词：
- “根据设计文档完成代码补全”
- “按设计文档实现”
- “先分析文档再分步开发”
- “每步都跑单测”
- “开发完成后生成总结报告”

## 输入要求

开始执行前，优先确认以下信息：
- 设计文档路径或当前正在使用的设计文档
- 已有测试文件、测试入口或单测命令
- 本次只涉及的功能范围、模块范围或代码边界

如果信息不完整，按下面顺序补齐：
1. 先定位设计文档。
2. 再定位与该设计最接近的测试文件、测试命令或验收方式。
3. 最后收敛到本次要补全的代码边界。

## 执行原则

执行时默认遵循以下精简原则，以减少无效输出和无关改动：
- 不假设未给出的需求；不清楚就提问或显式标记假设。
- 先做最小可验证改动，不额外扩展功能。
- 只修改与当前步骤直接相关的代码，不顺手重构无关内容。
- 每一步都要有明确的验证动作；验证失败时，先修当前步，不跳到下一步。
- 开发计划按“功能块”或“代码边界”拆分，不拆得过细。
- 输出保持简洁，优先给结论、风险、验证结果和下一步。

## 标准流程

### 第一步：分析设计文档并建立约束

目标：把设计文档转成可执行的开发边界和验收条件。

执行要点：
1. 提取目标功能、输入输出、关键流程、异常场景、接口约束。
2. 标记设计文档中可以直接映射到测试的行为要求。
3. 区分“必须实现”与“文档提到但本轮不做”的内容。
4. 明确现有代码中最靠近该行为的实现锚点：入口、服务、数据结构、测试。

产出要求：
- 一段简明问题定义
- 一组可验证的验收点
- 一份按功能块划分的开发计划

### 第二步：根据测试用例规划开发计划

目标：先以测试和验收方式组织开发顺序，再进入编码。

规划规则：
1. 优先复用已有测试；不主动补充测试。
2. 开发计划按功能或代码边界拆分，例如：
   - 数据模型或 schema
   - 核心 service 逻辑
   - DAO / 外部调用适配
   - 入口编排或命令行接口
3. 每个步骤必须包含：
   - 本步目标
   - 预期修改文件范围
   - 验证方式
   - 完成判定

计划格式使用以下模板：

```text
1. [功能块名称]
   目标: [本步实现的行为]
   代码范围: [涉及文件或模块]
   验证: [单测文件、测试命令或断言行为]
   完成判定: [通过什么结果视为完成]
```

约束：
- 不按函数级或语句级过度拆分。
- 若两个改动必须一起验证，可以作为同一个功能块。
- 若某一步无法定义验证方式，说明计划还不够好，需要先补足测试或验收条件。

### 第三步：按开发计划逐步完成代码生成

目标：严格按计划顺序实现，不并发开启多个未验证的开发步骤。

每一步都遵循以下循环：
1. 读取本步相关代码和相邻测试，形成一个局部、可证伪的实现假设。
2. 做最小必要代码修改，优先落在直接控制行为的位置。
3. 不修改与本步无关的模块、格式或注释。
4. 修改完成后立即执行本步验证。

推荐顺序：
1. 先补数据定义与边界约束。
2. 再补核心业务逻辑。
3. 最后补胶水代码、入口或集成层。

### 第四步：每一步完成后必须执行单测验证

这是强制门禁，不允许跳过。

验证顺序：
1. 优先运行与本步直接相关的最小单测。
2. 若没有更窄的测试入口，运行该功能相关测试文件。
3. 若项目或当前功能没有现成单测，则跳过该步单测验证，并在进度说明与总结报告中明确记录“该步无单测，已跳过验证”。
4. 仅当当前步骤存在相关单测且单测通过后，才进入下一步开发计划；若无单测，则按记录后继续下一步。

失败处理：
- 如果单测失败且问题就在当前步骤内，先修复当前步骤并重跑同一验证。
- 如果失败暴露了计划错误或定位错误，先回到最近的控制点，修正当前步骤计划，再继续。
- 不在验证失败时扩展范围做顺手优化。

每步完成标准：
- 本步代码已落地
- 本步单测通过，或该步无单测且已明确记录跳过验证
- 没有新增与本步直接相关的静态错误
- 可以用一句话说明“本步实现了什么，验证了什么”

### 第五步：全部开发计划执行完成后生成总结报告

开发完成后，生成一份简洁总结报告，默认输出到 `文档/` 目录。

建议文件名：
- `文档/开发总结报告.md`
- 如果同类报告较多，可使用 `文档/开发总结报告-功能名.md`

报告至少包含以下内容：
1. 设计文档来源
2. 本次开发范围
3. 开发计划与实际完成情况
4. 每一步对应的验证结果
5. 未完成项、风险项、后续建议

报告模板：

```markdown
# 开发总结报告

## 1. 设计文档
- 路径: [设计文档路径]
- 目标: [一句话概述]

## 2. 开发计划执行情况
| 步骤 | 功能块 | 结果 | 说明 |
|---|---|---|---|
| 1 | [功能块] | 已完成 | [核心变更] |

## 3. 验证结果
- [测试命令或测试文件]: 通过 / 未通过
- [关键断言或行为]: [结果]

## 4. 风险与遗留事项
- [风险或未完成项]

## 5. 总结
- [本次交付结论]
```

## 验证清单

在结束任务前，逐项确认：
- 已读取并提炼设计文档，不是凭空猜测实现。
- 已根据测试或验收方式制定开发计划。
- 开发计划按功能块划分，而不是过细拆解。
- 每个功能块完成后都执行了可用单测验证；无单测时已明确记录跳过。
- 没有在未通过验证时继续推进后续步骤。
- 最终生成了总结报告。

## 输出风格

为了降低 token 输出，默认采用以下输出方式：
- 计划只写必要步骤，不写冗长背景。
- 汇报以“当前步骤、验证结果、下一步”三项为主。
- 结论先行，细节只补充与当前决策直接相关的内容。
- 除非用户要求，不输出大段代码讲解或重复上下文。

## 成功标准

任务完成必须同时满足：
- 设计文档中的目标功能已在代码中落地。
- 开发计划中的每一步都有对应验证记录。
- 所有存在的目标单测已通过；无单测的步骤已明确记录跳过验证，或明确说明无法通过的阻塞原因。
- 已生成开发总结报告并记录风险与遗留项。
