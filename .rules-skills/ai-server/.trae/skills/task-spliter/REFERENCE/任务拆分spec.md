# Python 项目任务拆分规范

本规范用于指导 AI 在完成需求变更分析后，结合 Python 项目代码库已有实现，对本次变更进行结构化任务拆分，并生成可直接执行的研发任务文档。

## 任务目标

根据已完成的需求分析文档、代码链路分析结果和技术方案，输出一份面向研发执行的任务拆分文档。

任务拆分文档的目标不是重复需求分析，而是将“需要改什么”进一步转化为“具体要做哪些任务、这些任务属于哪一类、每类任务要产出什么”。

## 输入前提

生成任务拆分前，必须已经具备以下输入：

1. 本次需求的需求分析文档。
2. 代码库相关入口、调用链路、核心模块的分析结果。
3. 明确的改动点列表，包括新增点、修改点、复用点和影响点。
4. 已确认的边界条件、约束条件和待决议项。

如果上述信息不完整，不允许直接编造任务。应先补充待确认项，再进行任务拆分。

## 拆分原则

1. 基于真实代码拆分
   - 所有任务必须来自需求分析和代码分析的实际结论。
   - 不能脱离当前代码库结构，凭空设计模块或任务。

2. 面向交付物拆分
   - 任务应围绕最终产出进行拆分，例如数据库变更脚本、API Router、Service、Repository、Schema、接口文档、配置项、测试用例等。
   - 每个任务都应能对应明确的代码交付物或文档交付物。

3. 面向职责边界拆分
   - 不同职责的工作要分开，例如数据库设计、接口接入层实现、业务逻辑实现、异步任务处理、测试验证、接口文档生成。
   - 不要把多个职责完全不同的工作混在一个任务中。

4. 最大化复用、最小化改动
   - 若已有实现可复用，任务应描述为“扩展/复用已有能力”，而不是默认“新增一套”。
   - 若确需新增模块，必须能从需求分析中找到依据。

5. 粒度适中
   - 任务粒度要足够明确，开发人员或 AI 工具能够直接执行。
   - 不能过粗，例如“完成后端开发”。
   - 也不能过细到每一行代码都拆成单独任务。

6. 分类输出
   - 最终任务必须按任务类型分组输出，而不是按时间顺序堆叠。
   - 优先使用统一分类，保证不同需求输出风格一致。

## 任务拆分步骤

### 1. 识别本次变更涉及的交付物

根据需求分析和代码分析结果，先识别本次变更涉及哪些交付物类型，例如：

- 数据库表、字段、索引或数据库变更脚本
- 枚举、常量、配置项、环境变量
- API Router / View / Endpoint 接口定义
- Service 业务逻辑
- Repository / ORM Model / 持久化访问层
- Pydantic Model / dataclass / Schema / 请求响应模型
- 消息、异步任务、定时任务、后台作业
- 权限校验、参数校验、幂等与异常处理
- 接口文档
- 测试用例与验证脚本

### 2. 识别可复用点与必须新增点

对每类交付物，判断是以下哪一种：

- 直接复用已有实现
- 基于已有实现扩展
- 必须新增

输出任务时，要在任务描述中体现是“新增”“扩展”还是“复用接入”。

### 3. 生成任务分类

将识别出的交付物归入标准分类。默认按以下分类输出：

1. 数据库变更与初始化脚本
2. 数据结构与配置定义
3. 接口接入层实现
4. 业务服务与领域逻辑实现
5. 数据访问与持久化实现
6. 异步任务 / 消息 / 定时任务实现
7. 接口文档生成
8. 测试与验证任务
9. 发布、回滚与运维配套任务

如果某一类在本次需求中不存在，可以省略该分类，但不能伪造内容。

## 分类说明

### 1. 数据库变更与初始化脚本

适用于以下任务：

- 新增数据库表
- 新增索引、唯一约束
- 修改表结构或新增字段
- 编写 Alembic / SQL 初始化脚本
- 补充初始化数据或历史数据修复脚本

输出要求：

- 写清楚表名或结构对象名。
- 写清楚任务目标，例如创建、修改、补充索引、补充初始化数据。
- 如果是扩展现有表，也要明确写出扩展点。

### 2. 数据结构与配置定义

适用于以下任务：

- 新增枚举、常量、配置项
- 新增 Schema / Request / Response / Query / Command 模型
- 新增 Pydantic Model、dataclass、TypedDict 或其他项目统一数据模型
- 新增配置开关、灰度开关、字典项

输出要求：

- 明确结构名称。
- 说明该结构服务于哪个业务场景。

### 3. 接口接入层实现

适用于以下任务：

- 新增 Router / Blueprint / View / Endpoint
- 在现有接口模块下新增接口
- 修改已有接口入参、出参、行为

输出要求：

- 优先按 Router、业务接口模块或资源域维度聚合。
- 每个接口模块下列出具体接口职责。
- 若为扩展已有接口模块，需要写明是在哪个 Router、View 或 Endpoint 上扩展。

### 4. 业务服务与领域逻辑实现

适用于以下任务：

- Service 层逻辑新增或扩展
- 领域规则校验
- 流程编排
- 参数校验、状态流转、幂等控制、异常处理

输出要求：

- 说明核心业务动作。
- 说明依赖哪些已有服务或新增服务。

### 5. 数据访问与持久化实现

适用于以下任务：

- Repository、ORM Model、查询封装或持久化模块新增或扩展
- 查询、分页、批量写入、更新、删除能力实现

输出要求：

- 说明对应的数据对象。
- 说明核心持久化能力。

### 6. 异步任务 / 消息 / 定时任务实现

适用于以下任务：

- 新增异步处理任务
- 接入 MQ 消息生产/消费
- 新增 Celery / RQ / APScheduler / 自定义后台任务逻辑
- 定时任务扫描、补偿和重试逻辑

输出要求：

- 写清楚任务名称。
- 说明触发方式、执行目标和结果处理。

### 7. 接口文档生成

适用于以下任务：

- 生成或更新 OpenAPI / Swagger / Markdown 接口文档
- 补充字段说明、错误码说明、示例请求和示例响应

输出要求：

- 优先按 Router、接口模块或业务域输出。
- 与接口接入层实现分类保持对应关系。

### 8. 测试与验证任务

适用于以下任务：

- 单元测试
- 集成测试
- API 联调验证
- 数据初始化与回归验证
- 性能、兼容性、可靠性验证

输出要求：

- 写清楚覆盖的功能范围。
- 重点覆盖正常流程、异常流程和边界条件。
- 优先使用项目现有测试体系，例如 pytest、unittest、接口测试脚本等。

### 9. 发布、回滚与运维配套任务

适用于以下任务：

- 灰度开关配置
- 监控告警补充
- 回滚方案准备
- 配置项上线说明
- 数据库变更或初始化脚本执行顺序说明

输出要求：

- 仅在需求确实涉及上线配套改动时输出。

## 任务输出格式要求

最终任务必须使用分组编号格式输出。

要求如下：

1. 一级编号表示任务分类，例如 `1. 数据库变更与初始化脚本`。
2. 二级编号表示该分类下的具体任务，例如 `1.1 创建 xxx 表建表脚本`。
3. 二级任务名称必须直接体现交付物和动作，避免空泛描述。
4. 同一类任务尽量按业务对象聚合。
5. 若某类任务没有内容，可以不输出该分类。
6. 输出内容默认使用中文，关键对象名、表名、模块名、类名、函数名、接口名保留原始标识符。

## 任务命名要求

每个任务标题建议遵循以下模式之一：

- 创建 + 表/结构/模块名称
- 新增 + Router/View/Service/配置名称
- 扩展 + 现有模块名称 + 能力说明
- 生成 + 接口文档/测试用例/监控配置
- 实现 + 异步任务/消息处理/校验逻辑

避免使用以下模糊表述：

- 处理后端逻辑
- 补一些接口
- 改数据库
- 完成开发

## 输出内容约束

1. 任务必须与需求分析文档中的改动点一一对应。
2. 若某项属于复用现有能力，应明确说明复用对象，不要伪装成纯新增任务。
3. 若需求分析中未涉及数据库、接口或异步任务，则不得强行输出相关分类。
4. 若存在不确定实现，使用“待确认任务”或“待确认前置条件”单独列出，不要伪造确定性任务。
5. 输出的任务文档应能直接作为后续 AI 开发工具的输入。

## 推荐输出模板

可按以下模板生成任务拆分文档：

```md
# ${需求名称}任务拆分文档

## 1. 数据库变更与初始化脚本
1.1 创建 xxx 表建表脚本
1.2 扩展 xxx 表字段

## 2. 数据结构与配置定义
2.1 新增 xxx 请求模型
2.2 新增 xxx 枚举定义

## 3. 接口接入层实现
3.1 xxx 管理 Router（接口 A、接口 B）
3.2 xxx 查询 Router（接口 C、接口 D）

## 4. 业务服务与领域逻辑实现
4.1 实现 xxx 保存逻辑
4.2 实现 xxx 查询与分页逻辑

## 5. 数据访问与持久化实现
5.1 新增 xxx Repository 查询能力
5.2 扩展 xxx ORM Model 写入能力

## 6. 异步任务 / 消息 / 定时任务实现
6.1 新增 xxx 异步任务处理

## 7. 接口文档生成
7.1 生成 xxx 管理接口文档

## 8. 测试与验证任务
8.1 补充 xxx 单元测试
8.2 补充 xxx 接口联调与回归验证

## 9. 发布、回滚与运维配套任务
9.1 补充 xxx 监控告警配置
9.2 准备 xxx 回滚方案

## 10. 待确认事项
- [ ] [1] xxx 任务是否需要灰度发布
- [ ] [2] xxx 表是否复用现有索引策略
```

## 示例

以下示例展示输出风格，不代表所有需求都必须包含这些分类：

```md
# 服务包销售范围配置任务拆分文档

## 1. 数据库变更与初始化脚本
1.1 创建服务包销售端配置表建表脚本（service_package_sales_channel）
1.2 创建服务包售卖行业城市规则表建表脚本（service_package_sales_industry_city）
1.3 创建服务包售卖品牌表建表脚本（service_package_sales_brand）
1.4 创建服务包售卖连锁表建表脚本（service_package_sales_chain）
1.5 创建服务包售卖门店表建表脚本（service_package_sales_store）
1.6 创建异步任务表建表脚本（async_task）
1.7 创建服务包禁售名单表建表脚本（service_package_forbidden_list）

## 2. 接口接入层实现
2.1 销售端配置管理 Router（保存销售端配置接口、查询销售端配置接口）
2.2 售卖行业与城市配置管理 Router（添加规则接口、删除规则接口、修改规则接口、查询规则列表接口）
2.3 售卖品牌配置管理 Router（添加品牌、批量导入品牌、导出品牌数据、查询品牌列表）
2.4 售卖连锁配置管理 Router（添加连锁、批量导入连锁、导出连锁数据、查询连锁列表）
2.5 售卖门店配置管理 Router（添加门店、删除门店、批量导入门店、导出门店数据、查询门店列表）
2.6 异步任务管理 Router（查询任务列表、查询任务详情）

## 3. 接口文档生成
3.1 生成销售端配置管理接口文档
3.2 生成售卖行业与城市配置管理接口文档
3.3 生成售卖品牌配置管理接口文档
3.4 生成售卖连锁配置管理接口文档
```

## 非目标

- 不输出脱离当前代码结构的理想化任务清单。
- 不把需求分析全文重复粘贴到任务拆分文档中。
- 不把没有交付物指向的泛化建议当成任务。
