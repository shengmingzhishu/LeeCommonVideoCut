## 触发冲突解决规则

当用户请求可能匹配多个 Skill 时，按以下优先级选择：

### 规则 1：具体 > 抽象

| 用户说 | 优先 Skill | 原因 |
|--------|-----------|------|
| "设计一个页面" | `model-design` | 有明确产出物（HTML文件） |
| "写设计文档" | `docs-design` | 有明确产出物（文档文件） |
| "帮我设计前端"（无具体产出物） | `frontend-design` | 仅需创意方向，无具体文件 |
| "给我一套蓝色配色" | `ui-ux-pro-max` | 仅需 Token 值，无需设计哲学 |

### 规则 2：审计 > 设计

| 用户说 | 优先 Skill | 原因 |
|--------|-----------|------|
| "审查 UI 代码" / "这个设计好不好" | `web-design-guidelines` | 审计/评估场景 |
| "帮我设计/实现 UI" | `model-design` 或 `frontend-design` | 创建场景 |

### 规则 3：性能 > 通用

| 用户说 | 优先 Skill | 原因 |
|--------|-----------|------|
| "优化 React 性能" / "bundle 太大" | `vercel-react-best-practices` | 性能专项 |
| "用 React 实现这个页面" | `frontend-design` 或 `model-design` | 通用实现 |

### 规则 4：需求澄清 > 直接执行

| 用户说 | 优先 Skill | 原因 |
|--------|-----------|------|
| 需求模糊/一堆问题/不确定要什么 | `qa-reset` | 必须先澄清需求 |
| 需求清晰/单一任务 | 对应领域 Skill | 可直接执行 |

## 各 Skill 详细信息

### P0 - 核心技能（最高优先级）

#### qa-reset
- **定位**：需求润色与交互模式识别
- **强项**：双层识别机制（7 种交互模式 × 5 大内容维度）
- **何时使用**：需求模糊、批量问题、需要澄清/纠偏/评估时
- **输出**：结构化需求、执行计划、风险评估

#### karpathy-guidelines
- **定位**：编码准则（Andrej Karpathy 风格）
- **强项**：4 条核心原则（思考优先、简单优先、精准修改、目标驱动）
- **何时使用**：写代码、重构、Code Review 时
- **输出**：高质量、可维护的代码

### P1 - 重要技能

#### find-skills
- **定位**：技能发现与安装
- **强项**：质量验证（安装量>1K、来源信誉、GitHub stars）
- **何时使用**：用户问"有没有XX技能"/"帮我找个技能"
- **输出**：技能推荐列表 + 安装指导

#### project-analysis
- **定位**：项目分析器
- **强项**：7 个 Python 分析脚本（架构/依赖/质量/技术栈检测）
- **⚠️ 注意**：SKILL.md 声明"首选内置工具，非必要不调用 scripts/*.py"
- **建议**：脚本可能已死代码化，待 Phase 3 清理

### P2 - 常用技能

#### docs-design
- **定位**：项目级设计文档生成
- **强项**：版本管理（永不覆盖旧文件）、中文主题命名、内嵌原型
- **依赖**：ui-ux-pro-max（Design System 来源）
- **输出**：`/docs/{主题}-v{序号}.html`

#### model-design
- **定位**：独立 HTML 原型设计与维护
- **强项**：5 步工作流（分析→需求→Design System→HTML→迭代）
- **依赖**：ui-ux-pro-max（Design System 来源）
- **互补**：docs-design（文档 vs 独立原型）
- **输出**：单个 `.html` 文件（可直接浏览器打开）

#### vercel-react-best-practices
- **定位**：React 最佳实践与性能优化
- **强项**：Vercet 团队经验、性能清单、反模式
- **何时使用**：React 性能调优、bundle 优化、代码质量 Review
- **输出**：优化建议 + 代码改进

### P3 - 辅助技能

#### frontend-design
- **定位**：设计哲学 + 创意方向（Anthropic 官方）
- **强项**：反 AI 通用美学、品牌视觉识别度、字体/配色/动效哲学
- **可选依赖**：ui-ux-pro-max（当需要具体 Token 值时）
- **何时使用**：需要独特视觉风格、"不像 AI 生成的页面"
- **不做什么**：不提供具体的 hex 色值、font-family 名

#### ui-ux-pro-max
- **定位**：设计系统规则库（基础设施级）
- **强项**：50+ 风格、97 配色方案、57 字体搭配、99 UX 规则
- **角色**：被 model-design/docs-design/frontend-design 依赖
- **何时直接使用**：用户明确要求"配色方案"/"字体搭配"/"UX 规则"
- **输出**：CSS 变量、Design System Token

#### web-design-guidelines
- **定位**：Web 设计审计规范
- **强项**：全面的设计检查清单
- **⚠️ 注意**：依赖外部 GitHub URL（网络不稳定时会失败）
- **何时使用**：UI 审计、设计 Review、代码质量检查

## 使用示例

### 示例 1：用户要求"帮我设计一个 Dashboard 页面"

```
用户输入: "帮我设计一个 Dashboard 页面"

触发分析:
- "设计" → 可能匹配 model-design / frontend-design / ui-ux-pro-max
- "Dashboard 页面" → 有明确产出物（页面）

决策路径（按优先级规则）:
1. 具体产出物? → 是（页面）→ 优先 model-design
2. 需要 HTML 原型还是 React 组件?
   - 如果是快速验证 → model-design（独立 HTML）
   - 如果是正式开发 → frontend-design（React 组件）

最终选择: model-design（假设是快速原型验证）

执行流程:
1. model-design 调用 ui-ux-pro-max 获取 Design System
2. 生成 Dashboard HTML 原型
3. 输出 Design System 摘要
```

### 示例 2：用户要求"这个页面的 UI 不太对，帮我审查一下"

```
用户输入: "这个页面的 UI 不太对，帮我审查一下"

触发分析:
- "审查" → 匹配 web-design-guidelines（审计场景）

决策路径:
1. 审计 > 设计 → web-design-guidelines

最终选择: web-design-guidelines

执行流程:
1. 读取页面代码
2. 按 Checklist 逐项检查
3. 输出问题列表 + 改进建议
```

### 示例 3：用户要求"我有一堆需求，不知道从哪开始"

```
用户输入: "我有一堆需求，不知道从哪开始"

触发分析:
- "一堆需求"、"不知道从哪开始" → 需求模糊 → qa-reset

决策路径:
1. 需求澄清 > 直接执行 → qa-reset（P0 最高优先）

最终选择: qa-reset

执行流程:
1. 识别交互模式：批量编排（一堆需求）
2. 识别内容维度：需求设计
3. 输出：结构化需求清单 + 执行计划 + 优先级排序
```

## 维护指南

### 新增 Skill

1. 在本文件"快速查找表"中添加一行
2. 在"依赖关系图"中添加节点和边
3. 在"各 Skill 详细信息"中添加详细描述
4. 更新"触发冲突解决规则"（如有必要）
5. 更新版本号和日期

### 废弃 Skill

1. 在"快速查找表"中将状态改为"🚫 已废弃"
2. 在"依赖关系图"中移除节点（或标记为废弃）
3. 记录废弃原因和替代方案
4. 不要立即删除文件（保留至少一个版本周期）

### 更新 Skill 依赖

1. 修改对应 Skill 的 SKILL.md frontmatter
2. 更新本文件的"依赖关系图"
3. 更新"快速查找表"中的依赖列
4. 更新版本号和日期
